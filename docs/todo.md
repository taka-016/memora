# ToDo List

## DB設計・リポジトリ・ユースケース・DTO・マッパー関連

### Firestoreの永続キャッシュ・保存完了確認・楽観的排他（オンラインのみ）

サーバーでの保存完了を確認し、古い編集内容による上書きを防ぐ排他制御を導入してから永続キャッシュを有効化する。設計判断は[ADR-009〜ADR-013](adr.md#adr-009-オンラインの保存成功はサーバーでの書き込み完了で判定する)に従う。対象はFirestoreを使うオンラインモードとする。

最小限の改修を大前提とし、既存の取得・全件置換・保存フロー・トランザクションをできるだけ維持する。バージョン導入と親のバージョンによる排他に必要な変更を中心に、合意済みの保存状態・キャッシュの対応だけを行う。

今回の実装範囲は次のとおりとする。

| 対象 | 競合単位・適用経路 |
| --- | --- |
| `trip_entries`・`locations`・`tasks`・`itinerary_items` | 旅行全体。親の`version`を共有し、子だけの変更にも適用する |
| `groups`・`group_members` | グループと所属メンバー全体。メンバーの削除は退避へ変更し、所属関係を削除しない |
| `members`・`member_invitations`・`group_events` | 各ドキュメント。メンバー編集、招待承認によるメンバー更新、招待の再発行、グループイベント編集に適用する |
| `member_events` | メンバーと年の組。固定IDへの保存にも適用する |
| `calendar_events`・`calendar_event_overrides` | 予定全体。個別回の変更・取消し、系列分割・置換に適用し、既存トランザクションと系列分割時の照合を維持する |
| `calendar_labels` | 各ラベル。編集・並べ替えに適用し、内部の参照件数更新と編集の競合を区別する |
| `dvc_point_contracts` | グループ内の契約一覧全体。専用の親ドキュメントの`version`を使用し、親の更新と契約一覧の置換を同じバッチで行う。`groups.version`は使用しない |
| `dvc_point_usages`・`dvc_limited_points` | 現在は追加・削除のみであり、更新排他の対象外。保存完了確認は対象とする |

グループ・メンバーの退避は[ADR-008](adr.md#adr-008-グループとメンバーは削除済み保存先へ移動し関連データを残す)、それ以外の物理削除は[ADR-012](adr.md#adr-012-独立した物理削除には期待バージョン照合を追加しない)、通常取得と再取得の扱いは[ADR-013](adr.md#adr-013-通常の取得結果で編集し確認用の再取得を追加しない)に従う。

以下の番号順に対応する。各段階で重要な成功・失敗ケースを検証し、未完了の段階を残したままキャッシュを有効化しない。

#### 1. 保存完了確認と通信断時の操作状態

- 上表の全保存経路について、RepositoryからUseCase・Notifier・画面まで保存処理の完了と例外が伝わることを確認する。サーバーでの保存完了後だけ成功表示・画面遷移・後続処理を行い、既存の`await`で満たしている経路には確認用処理を追加しない
- キャッシュへの反映や監視通知を保存成功として扱わない。必要な監視経路では`hasPendingWrites`などのメタデータで未確定の書き込みを区別する
- 通信断でも既存の保存中状態と完了待ちを利用し、既存の重複操作抑止を確認する。不足する経路だけを修正し、新しい保存状態管理方式は追加しない。タイムアウトは書き込みを取り消さないため、結果未確認を保存失敗と断定せず、無条件に再送しない
- 保存成功、サーバーによる拒否、通信断からの復旧、複数書き込みの途中失敗を検証する。永続化後に保留書き込みが再送されるケースは第5段階でも確認する

#### 2. 単一ドキュメントの楽観的排他と競合時の復旧

- `members`・`member_invitations`・`group_events`・`member_events`の取得結果、編集状態、保存要求へ整数の`version`を追加する。メンバーイベントはメンバーと年の組の初回作成と既存更新を区別し、編集開始時に存在しなかったデータが他端末で作成済みなら上書きしない
- 編集開始時の`version`をMapper・DTO・Entity・UseCase・Notifier・画面の間で保持する。招待承認によるメンバー更新と招待の再発行でも取得時の値を引き継ぎ、Firestore固有の型を内側の層やPresentation層に持ち込まない
- 作成時は`version = 1`、更新時は編集開始時の`version + 1`を固定値として送る。`FieldValue.increment(1)`や、保存直前に取得した最新版のバージョンへの差し替えで古い編集内容を保存しない
- [firestore.rules](../firestore.rules)の包括的な書き込み許可をコレクション別の条件へ置き換え、メール確認済みの認証ユーザーという現行条件を維持する。対象データの作成時は整数の初期値1、更新時はサーバーの現在値より1大きい整数を検証し、バージョン未設定・削除・不正な型・据え置きを拒否する。独立した削除にはバージョン照合を追加しない。対象外のコレクションへの許可を残す場合も、対象更新を別の一致するルールで迂回できない構成にする
- メンバーイベントの固定IDへの保存と既存重複ドキュメントの整理を確認し、重複整理が拒否された保存の後に実行されないようにする。空メモによる削除と重複整理の既存処理は維持し、一覧の強制サーバー取得は追加しない
- 更新拒否時は既存の失敗処理とエラー表示を利用し、入力を残して編集し直せるように必要な経路だけ修正する。Rulesの`permission-denied`を一律に競合と断定せず、原因を特定するための追加取得や専用の復旧フローは作らない
- Firestore Emulatorで同じバージョンからの同時保存の一方だけが成功すること、固定IDへの同時初回保存、古いキャッシュからの更新、不正なバージョン、認証・権限拒否、包括的な許可による迂回の拒否を検証する。関連するアプリのテストで競合後の入力保持と復旧を確認する

#### 3. 親子データ・バッチ・既存トランザクションへの適用

- 旅行の作成・全体編集・場所・タスク・旅程の編集を、`trip_entries.version`と親子の同一バッチで保護する。子だけの変更でも親を更新し、親の競合時はバッチ全体を拒否する。既存の共有`FirestoreWriteContext`を使う経路にも適用する
- グループの作成・編集・所属メンバーの全件置換を、`groups.version`と同一バッチで保護する。メンバーの退避では所属関係を削除しない。退避中のメンバーを画面から除外しても、グループ編集の全件置換でその所属を失わず、退避したメンバーの所属情報が残る保存要求にする
- 親子の編集では通常の取得結果と取得時の親バージョンを保持し、編集開始時のサーバー再取得や親バージョンの前後照合は追加しない。取得済みの内容と期待バージョンを保存要求へ引き継ぐ
- 子データの全件置換は既存の処理と保存時の対象一覧取得を維持し、親のバージョン照合を追加する。編集開始時の一覧・削除対象IDを新たに保持する方式への変更や、保存確認・競合確認のための追加取得は行わない。他端末による子の追加・更新・削除は親のバージョン変更で検出し、古い要求は全体を拒否する。旅行・予定など、物理削除を維持する親の削除に伴う子の削除は既存処理を維持し、残存防止のために`FirestoreWriteContext.get()`などへ一律に`Source.server`を指定しない
- 予定と個別回には`calendar_events.version`を追加し、個別回だけの変更・取消しでも親のバージョンを更新する。既存の作成・更新・系列分割・置換トランザクション、ラベル参照件数の調整、系列分割時の内容照合を維持する。既存トランザクションの自動再試行でも編集開始時の期待バージョンを照合し、最新版の値へ差し替えない
- 色ラベルの作成・編集・並べ替えへバージョンを追加する。並べ替え要求は各ラベルの編集開始時のバージョンを保持し、一件でも競合すれば全体を拒否する。予定操作に伴う`eventCount`だけの内部更新では編集用バージョンを変更せず、その許可条件から名前・色・順序・バージョンを変更できないようにRulesの変更フィールドを限定する
- DVC契約一覧にはグループごとの専用の親ドキュメントと整数の`version`を用意し、その期待バージョンを一覧取得から編集・保存まで保持する。`groups.version`は参照・更新せず、書き込み対象を決める既存の一覧取得を利用する。競合確認用の追加取得は行わない。`SaveDvcPointContractsUsecase`の既存の全削除・作成処理を、親のバージョン更新と同じバッチへまとめる。空一覧の保存でも親を更新し、途中失敗で契約一覧が欠落しないようにする。オフラインの既存動作を維持する
- 子の作成・更新・編集に伴う削除について、Rulesの`get()`・`getAfter()`で親のバージョン更新との同時実行を検証する。親のバージョン更新を伴わない子の書き込みや親参照の付け替えによる迂回を拒否する。旅行・予定などの親の物理削除と、それに伴う子の削除には親のバージョン更新を要求せず、親が削除済みの場合の子の削除も認証条件を維持して許可する
- Rulesの追加読み取り課金とアクセス回数を確認し、1操作10回、バッチ・トランザクション全体20回の制限内で、複数旅行・複数グループ・複数ラベルを扱う経路も検証する。原子性を失う分割は行わない。合意した追加読み取りを超える通信や実装の複雑性が必要なら、実装前にユーザーと方針を再確認する
- 親子の同時編集、異なる子の編集による競合、子の追加・変更・削除、直接の子更新の拒否、バッチ全体の競合拒否、古い取得結果からの保存の拒否、既存の対象一覧取得を用いる置換、旅行・予定の親削除と配下の削除（親が削除済みの場合を含む）、メンバー退避中のグループ編集による所属の保持、予定・個別回・系列分割、ラベル編集・並べ替えと内部件数更新、DVC契約一覧の同時保存・空一覧・途中失敗、グループ編集とDVC契約編集が互いのバージョンに影響しないことを検証する

#### 4. 既存データの初期化とアプリ・Rulesの導入

- 第2段階の単一ドキュメントと第3段階のバージョンを管理する親・ラベルに初期値`version = 1`を設定する管理処理を用意する。子はそれぞれの親のバージョンで管理し、子ごとの独立した編集用バージョンは追加しない。DVC契約一覧の専用の親ドキュメントは契約が空のグループにも用意し、初期値`version = 1`を設定する。初期化対象と件数、不正な既存値、完了状況を確認できるようにし、再実行で初期化済みのバージョンを巻き戻さない
- 移行前のバックアップと、書き込み停止・初期化・検証・厳格なRulesへの切替の手順を用意する。初期化失敗や未初期化データがある場合は書き込みを再開せず、データを保持して復旧する
- 第2・第3段階の対応アプリを永続キャッシュ無効のまま配布する。初期化前は対象編集を利用不可として扱い、欠けたバージョンをアプリ側で補完して保存しない
- クライアントの書き込みを一時停止するRulesを適用してから、管理処理で既存データを初期化する。初期化とクライアント更新が競合しない状態で対象全件のバージョン設定を検証し、その後に第2・第3段階の厳格なRulesへ切り替える
- 旧アプリの対象データの作成・更新と、親のバージョン更新を伴わない子の置換を拒否する。バージョン未設定の更新を恒久的に許可する互換条件は設けない。旧アプリからのグループ・メンバーの物理削除と関連データの連鎖削除を許可せず、退避に対応したアプリとRulesの導入順序を合わせる。それ以外の独立した削除への排他を見送る方針は維持する
- Firestore Emulatorで移行前データ、初期化の再実行、途中失敗からの復旧、書き込み停止中の拒否、初期化漏れの検出、切替後の対応アプリの成功と旧形式の対象書き込みの拒否を検証する。実環境への切替は準備・検証を完了してから実施する

#### 5. 永続キャッシュの有効化と最終確認

- 第1〜第4段階の対象保存経路とRulesの導入・検証が完了した後、`OnlineAppServices.initialize()`の`persistenceEnabled`を`true`にする。キャッシュ容量はSDKの既定値を使用する
- 閲覧・編集では通常の取得によるキャッシュ利用を許可し、編集開始時・保存前の最新化のための再取得は追加しない。通常の`get()`はサーバーから取得を試み、接続できない場合にキャッシュを利用するため、キャッシュ有効化だけで常にキャッシュ優先になるわけではないことを確認する
- 実SDKでアプリ再起動後のキャッシュ読取、保留書き込みの復旧、保存完了の表示、古いキャッシュからの競合拒否、Rules切替後の旧形式の保留書き込みの拒否を検証する。キャッシュにないデータの取得失敗を空データとして扱わないことも確認する
- オンライン側の変更がSQLiteのオフラインモードとAndroidウィジェットの既存動作に影響しないことを確認し、`./check.sh online`と`./check.sh offline`で検証を完了する

### グループ・メンバー削除時の退避

[ADR-008](adr.md#adr-008-グループとメンバーは削除済み保存先へ移動し関連データを残す)に従い、削除時の親の情報を退避先へ移し、元の`groups`・`members`から削除する処理をオンライン・オフラインの双方へ実装する。目的は誤削除後もデータが残っていることであり、復活用の処理・画面・操作手順は実装・設計しない。

#### 1. 退避用の保存先の追加

- Firestoreに削除済みグループ・削除済みメンバー用のコレクション、SQLiteに対応する専用テーブルを追加する。削除時の親の情報を元のIDとともに保持し、オンラインのバージョン情報を含む既存の内容を欠落させず保存する
- SQLiteの親の削除に伴う外部キーの連鎖削除・参照制約を確認し、元の`groups`・`members`から行を削除しても関連データ・担当・所属を保持できる参照構造へ変更する。通常テーブルに親の行を残して非表示にする方式にはしない。復活機能のための追加構造や旧形式向けの互換処理は追加しない
- ユーザーストーリー・ユースケース図・ER図を、グループ・メンバーの削除時に親を退避し、関連データを残す仕様へ合わせる

#### 2. 削除処理の退避への変更と検証

- `DeleteGroupUsecase`とRepositoryのグループ削除を、退避用保存先への追加と元の`groups`からの削除へ変更する。旅行・場所・タスク・旅程、グループイベント、カレンダー予定・個別回・ラベル、DVCデータ、所属メンバーは削除せず、関連データの削除呼び出しを外す
- `DeleteMemberUsecase`とRepositoryのメンバー削除を、退避用保存先への追加と元の`members`からの削除へ変更する。グループへの所属、メンバーイベント、タスク担当などは残し、所属解除とメンバーイベント削除の呼び出しを外す
- 退避の保存が成功する前に元データを削除しない。退避保存と元の`groups`・`members`からの削除を同じ原子的な書き込みで行える構造にし、保存処理の完了と例外を呼び出し元へ伝える
- 通常の取得では退避先を参照してグループ・メンバーを表示せず、削除後に通常の一覧・選択・操作対象から外れる振る舞いを維持する。保持した関連データからの取得やAndroidウィジェットでも退避した親を表示しないよう、必要な取得経路だけを調整する。削除済み一覧、復活用のRepository・UseCase、復活操作、復活後の表示更新、復活に関するバックアップ・復元対応は追加しない
- Firestore Rulesに退避用保存先の書き込み条件を追加し、現行の認証条件を維持する。旧アプリのグループ・メンバー削除で関連データを消さないよう、削除処理とRulesの導入順序を合わせる
- 両モードで削除時の退避情報と元のIDの保持、関連データ・所属・担当が削除されないこと、退避保存の失敗時に元データを失わないこと、成功時には元の`groups`・`members`に存在しないこと、通常表示・選択・ウィジェットからの除外を検証する。SQLiteでは外部キーの連鎖削除・参照の切断が起きないことも確認する
- `./check.sh online`と`./check.sh offline`を実行し、既存の旅行・予定などの個別削除とFirebase Authenticationのアカウント削除が今回の変更によって変わらないことを確認する

### 6. 本人のGoogleカレンダー連携（ストーリー25・オンラインのみ）

- Composition Rootでモード別に依存実装を選択し、オフラインでは連携の入口を利用不可にしてGoogleカレンダーのSDK初期化と通信を行わない
- Googleカレンダーの認証・読取処理と、本人単位の連携設定・表示対象カレンダーの保存処理を追加する。設定を他のメンバーが読み書きできないようにする
- 外部予定はグループの予定として保存・共有せず、Googleカレンダーへの作成・編集・削除や双方向同期を行わない
- 本人が表示対象のGoogleカレンダーを選択し、その予定をグループの予定と同じ日付に読み取り専用で重ねて表示する。連携元のカレンダー名を表示し、グループ切替後も本人の外部予定を表示する
- Googleカレンダーからの読取では、外部の繰り返し予定も個別回の変更・取消しを反映して表示する。外部予定の繰り返し設定は読み取り専用とする
- 再取得で外部の変更を反映し、取得失敗を表示して再認証・再試行できるようにする。外部予定の取得状態をグループの予定と分け、失敗時もグループの予定を表示する
- 連携解除で本人の連携設定・表示対象を解除し、外部予定の表示を終了する。Googleカレンダーの予定とグループの予定は削除しない
- 本人だけへの表示・設定アクセス、取得元の識別、グループ切替後の継続表示、再取得、取得失敗時のグループ予定表示、再認証・再試行、連携解除、オフラインでの初期化・通信の抑止をテストする

### 補足: カレンダー関連モデル（Googleカレンダー連携は実装予定）

[ユーザーストーリー23〜25](user_stories.md)と[ADR-004](adr.md#adr-004-グループの予定と個人の外部予定を分離して扱う)および繰り返し設定の追加要望に対応する設計を示す。[ER図](er_diagram.md)の`calendar_events`と`calendar_labels`は単発予定の保存基盤をFirestore・SQLiteへ実装済み。`calendar_events.recurrenceRule`・`timeZone`と個別回の上書きは実装済み。繰り返しの入力画面と個別回・系列の編集・削除は実装済み。`google_calendar_connections`・`google_calendar_selections`は実装予定。Firestore・SQLiteともに個別回の変更・取消しを`calendar_event_overrides`に保存する。現在の保存構造は[ER図の補足](er_diagram.md#図の補足)を参照。

| エンティティ | 役割 | 保存・公開範囲 |
| --- | --- | --- |
| `calendar_events` | グループに属する予定のタイトル・期間・終日区分・色ラベル・繰り返しルール | オンラインはFirestoreで所属メンバーに共有、オフラインはSQLiteで端末内のみ |
| `calendar_event_overrides` | 繰り返し予定の個別回の変更・取消し | 親の予定と同じ保存・公開範囲 |
| `calendar_labels` | 誰に関係する予定かを表すグループごとの名前と色 | 予定と同じ保存・公開範囲 |
| `google_calendar_connections` | 本人と連携先Googleアカウントの対応 | オンラインのみ、連携した本人だけが読み書き可能 |
| `google_calendar_selections` | 本人が表示対象として選択したGoogleカレンダーのID | オンラインのみ、連携した本人だけが読み書き可能 |

- `calendar_events`は日付単位の予定であり、年表セルのメモである既存の`group_events`・`member_events`とは別に管理する。
- 予定は必ず1つのグループと1つの色ラベルに属する。予定の`groupId`とラベルの`groupId`は一致させる。タイトルは空にできず、終了日時は開始日時より前にできない。終日・複数日の予定も開始と終了の組で表す。
- `calendar_events.recurrenceRule`は未設定なら単発予定、設定時はRFC 5545のRRULE形式で上記の繰り返し条件を表す。開始・終了日時は初回を表し、時刻付きの系列は`timeZone`にIANAタイムゾーンIDを保持する。終日予定の日時欄は日付として解釈し、端末のタイムゾーン変更で日付をずらさない。
- `calendar_event_overrides`は`eventId`と`originalStartDateTime`の組で一意とする。元の開始日時（終日は元の開始日）をキーにし、実際の日時を変更してもキーは変更しない。`isCancelled`が真ならその回を非表示にし、偽なら変更後のタイトル・期間・終日区分・色ラベルをすべて必須で保存する。取消し時はこれらの変更後の値を不要とする。
- 個別回の上書き情報は繰り返しルールを持つ親予定にのみ属し、親のグループ・タイムゾーンに従う。個別回の上書き情報のラベルも親と同じグループに限定する。親の削除・系列の分割・ルール変更では、個別回の上書き情報の参照整合性と適用範囲も合わせて維持する。
- 色ラベルの名前は特定のメンバーや「家族全員」などを表し、予定の登録者とは独立して指定する。共通ラベルも扱うため、ラベルと`members`の直接参照は必須にしない。ラベル変更・削除時も予定の参照整合性を維持する。
- Googleカレンダー連携の`memberId`は連携した本人を表す。グループへの外部キーを持たせず、グループ切替にかかわらず本人の設定を利用する。表示対象は`memberId`と`calendarId`の組で一意とし、連携解除時に連携設定と表示対象を削除する。
- 外部予定の本文・期間・連携元カレンダー名はGoogleカレンダーから取得して表示し、`calendar_events`へ保存しない。連携解除でもGoogleカレンダーとグループの予定は削除しない。認証情報の安全な保存方法は実装時に検討し、この業務モデルにはトークンや秘密情報を含めない。
- オフラインでは予定・繰り返しルール・個別回の上書き情報・色ラベルをバックアップ・復元の対象に含める。Googleカレンダー連携設定と表示対象はオフラインの保存・復元対象に含めない。
