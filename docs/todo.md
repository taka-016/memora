### 6. 本人のGoogleカレンダー連携（ストーリー25・オンラインのみ）

[ユーザーストーリー25](user_stories.md#25-オンラインモードのユーザーとして別のサービスで管理している自分の予定も一緒に確認したい予定の確認先を行き来したくないから)と[ER図](er_diagram.md)に沿い、以下の節・各節の番号順に実装・検証する。

#### 1. 連携設定の保存とモード別の依存を追加する

1. `google_calendar_connections`（`memberId`・`googleAccountId`）と`google_calendar_selections`（`memberId`・`calendarId`）のEntity・DTO・Mapper・Repositoryを追加する。設定はグループに紐付けず、表示対象は本人とカレンダーIDの組で一意に保存する。
2. Firestoreの保存・取得・削除処理とRulesを追加し、連携した本人だけが設定を読み書きできるようにする。
3. Composition Rootでオンライン用の依存を選択し、オフラインでは連携の入口を利用不可にする。連携設定はSQLite・バックアップ・復元の対象に追加しない。
4. 設定の保存・取得・削除、本人以外のアクセス拒否、オフラインでの連携処理の抑止をテストする。

#### 2. Google認証とカレンダー・予定の取得を追加する

1. Googleカレンダーの読み取り用の認証処理を追加する。認証情報の保存方法を選定して実装し、連携設定のEntity・DTO・Firestoreにはトークンや秘密情報を含めない。
2. 本人が利用できるカレンダーの一覧取得と、選択したカレンダーの表示期間内の予定取得を追加する。
3. 外部予定の本文・期間・終日区分・連携元カレンダー名を表示用データへ変換し、繰り返し予定の個別回の変更・取消しを反映する。`calendar_events`には保存せず、Googleカレンダーへの書き込み処理は追加しない。
4. 認証成功・失敗、カレンダー一覧と期間内予定の取得、繰り返し予定の変更・取消し、オフラインでのSDK初期化・通信の抑止をテストする。

#### 3. 表示対象の選択と共有予定への重ね合わせを追加する

1. Googleカレンダーへの連携操作と、表示対象カレンダーの選択・保存・再読込を行う画面とUseCase・Notifierを追加する。
2. 選択した外部予定をグループの予定と同じ日付に重ねて表示し、連携元のカレンダー名を付ける。外部予定とその繰り返し設定は読み取り専用で表示する。
3. 本人の外部予定をグループ切替後も表示し、他メンバーには公開しない。
4. 選択内容の保存・再読込、同じ日付への表示、取得元の識別、編集操作の抑止、本人だけへの表示、グループ切替後の継続表示をテストする。

#### 4. 再取得・エラー表示・再認証を追加する

1. 外部予定の取得状態をグループ予定と別に管理し、再取得操作でGoogleカレンダー側の変更を反映する。
2. 取得失敗の表示と再試行・再認証の操作を追加し、失敗時もグループの予定を表示する。
3. 再取得による変更反映、取得失敗中の共有予定表示、再試行と再認証による復旧をテストする。

#### 5. 連携解除を追加する

1. 本人の連携設定・表示対象を削除するUseCaseと解除操作を追加し、解除後は外部予定の表示を終了する。Googleカレンダーとグループの予定は削除しない。
2. 連携解除後に設定が削除されて外部予定が表示されず、Googleカレンダーとグループの予定が保持されることをテストする。

### 7. グループのカレンダーをオンラインのみStream化する（ストーリー23・24）

[ユーザーストーリー23](user_stories.md#23-ユーザーとして家族や友人の予定を記録し日付ごとにまとめて把握したい互いの予定を見落とさず調整したいから)・[24](user_stories.md#24-ユーザーとして予定が誰に関係するものか見分けたい自分や家族の予定を取り違えずに調整したいから)、[ER図](er_diagram.md)、[ADR-006](adr/adr-006-atomic-aggregate-updates.md)、[ADR-007](adr/adr-007-cached-read-consistency.md)に沿い、以下の順に実装・検証する。対象はアプリ内のグループ予定と色ラベルとし、Googleカレンダー連携は含めない。

#### 1. オンライン用の監視インターフェースと依存を追加する

1. Application層に、グループIDを指定して予定・色ラベルのDTO一覧を受け取る監視用QueryServiceインターフェースとUseCaseを追加する。既存のFutureによる取得用QueryService・UseCaseは維持し、SQLite側に監視実装を追加しない。
2. Firestoreの予定・色ラベルの監視実装をComposition Rootへ接続し、オンラインでは監視、オフラインでは既存の単発取得を使用する依存を構成する。Presentation層からFirestoreやSQLiteを直接参照しない。

#### 2. Firestoreの差分受信と個別回の取得を実装する

1. `calendar_events`・`calendar_labels`をグループIDで絞って`snapshots()`で監視する。初回通知で一覧を構築し、予定の追加・変更・削除とラベルの内容・並び順の変更を反映する。取得範囲は現在のグループ全件を維持する。
2. 予定の初回取得・追加・変更時に、`FirestoreCalendarEventStore`を利用して親の`overrideIds`が示す個別回を取得する。個別回の変更・取消しでも親予定が更新される既存契約を利用し、個別回の独立した監視は追加しない。変更のない予定の個別回は再取得せず、親の削除時は保持データから取り除く。
3. 個別回の非同期取得中に同じ予定の再変更・削除や購読の切り替えが発生しても、古い取得結果で新しい表示を上書きしないようにする。取得・変換失敗を通知でき、再試行では個別回も再取得できるようにする。
4. Firestore監視の初回取得、予定・ラベルの追加・変更・削除、個別回の変更・取消し、取得の前後逆転、取得失敗からの復旧をテストする。変更のない予定の個別回への追加読み取りが発生しないことも確認する。

#### 3. CalendarNotifierの受信・保存・エラー状態を調整する

1. `CalendarNotifier`で監視結果を`CalendarState`と元の予定一覧へ反映し、選択日・表示月を保持して繰り返し予定を再展開する。初回取得状態と予定・ラベルそれぞれのエラーを管理し、一方の受信成功で他方のエラーを消さない。
2. オンラインの通常の保存成功後は全件再取得を行わず、監視結果で画面を更新する。保存完了と表示更新の成否を分け、保存成功後の受信・取得失敗を保存失敗として扱わない。オフラインは画面表示時・保存後の既存の再取得を維持する。
3. 予定・色ラベルの編集入力と期待バージョンを編集開始時の値で保持し、自動更新で差し替えない。同じ予定の更新・削除と同じ繰り返し系列内の変更は既存の楽観的排他で拒否し、競合時も入力を保持する。予定追加や別予定の変更をカレンダー全体の競合として扱わない。
4. 色ラベルの並べ替えについて、楽観的に変更した表示と監視結果の反映を調整し、保存失敗時に古い一覧で他者の更新を上書きしないようにする。
5. グループ切り替え・Provider破棄・監視の再試行時に旧購読を解除し、旧グループの結果を反映しない。カレンダー本体とDialog・予定一覧で購読を共有し、再描画・日付選択・月移動・通常保存で購読を作り直さない。

#### 4. モード別の更新操作とエラー表示を実装する

1. `CalendarScreen`の手動更新ボタンはオフラインで維持し、オンラインでは通常の手動更新ボタンを表示しない。監視・個別回取得・変換のエラー時は、失敗内容と購読・取得を再開する再試行操作を表示する。
2. 初回取得失敗時は取得できていない状態を表示し、表示後のエラー時は直前の予定・ラベルを残して自動更新できていないことを伝える。編集可否は既存の取得エラー時の制御を維持する。
3. オンラインモードでの一時的な通信断はFirestore SDKのキャッシュ・再接続に任せ、アプリ独自の定期取得や無制限の再購読を追加しない。親子の取得時点をそろえるための検証・再取得は追加しない。

#### 5. モード別の動作と通信を検証する

1. Notifier・画面のテストで、外部更新の自動反映、選択日・月の保持、初回取得失敗、取得済み表示の保持、予定とラベルの部分的な失敗、再試行、保存成功後の表示更新失敗を検証する。
2. 編集中の外部更新で入力・期待バージョンが変わらないこと、同一予定・同一系列の競合拒否、別予定の更新や他者の追加によって予定追加が競合しないこと、ラベル並べ替え中の通知と保存失敗を検証する。
3. グループ切り替え・画面破棄・再試行で購読が重複せず、解除後の結果が反映されないことを検証する。オフラインで監視を開始せず、手動更新ボタンと画面表示時・保存後の再取得が維持されることも検証する。
4. オンラインの複数端末またはエミュレーターで通常予定・繰り返し予定・個別回・色ラベルの変更反映、通信断からの復帰を確認する。保存後の全件再取得、月移動による再購読、無関係な予定の個別回再取得が発生しないことを確認する。
5. `./check.sh online`と`./check.sh offline`でフォーマット・解析・テストを実行し、両モードの既存動作への影響を確認する。
