## DB設計・リポジトリ・ユースケース・DTO・マッパー関連

### 3. Firestoreの永続キャッシュ・保存完了確認・楽観的排他（オンラインのみ）

[ADR-004](adr/adr-004-archive-groups-and-members.md)・[ADR-005](adr/adr-005-version-based-concurrency-control.md)・[ADR-006](adr/adr-006-atomic-aggregate-updates.md)・[ADR-007](adr/adr-007-cached-read-consistency.md)に従い、以下の節・各節の番号順に実装・検証する。

#### 1. 保存完了・失敗を画面へ伝える

1. メンバー・招待・年表イベント・旅行・グループ・予定・ラベル・DVCの保存経路で、RepositoryからUseCase・Notifier・画面まで完了待ちと例外伝播が欠けている箇所を修正する。成功表示・画面遷移・後続処理はサーバー保存完了後に実行する。
2. 監視通知で保存成功を判定している経路は、未確定の書き込みを`hasPendingWrites`等で区別する。
3. 通信断時の重複操作抑止が欠けている画面を既存の保存中状態で制御する。結果未確認のタイムアウトを保存失敗として再送する経路を修正する。
4. 保存成功・サーバー拒否・通信断からの復旧・複数書き込みの途中失敗をテストする。

#### 2. バージョンの受け渡しと共通Rulesを実装する

1. 単独データ（`members`・`member_invitations`・`group_events`・`member_events`）、集約の親（`trip_entries`・`groups`・`calendar_events`・`dvc_point_contracts`）、`calendar_labels`のMapper・Entity・DTOへ整数の`version`を追加する。子は親のバージョンで管理する。
2. 取得・編集開始から保存・削除・退避要求まで期待バージョンを引き継ぐ。作成時は1、更新時は編集開始時の値+1を送り、トランザクション再試行でも期待値を保持する。Firestore固有の型はInfrastructure層に閉じ込める。
3. [firestore.rules](../firestore.rules)の包括的な書き込み許可をコレクション別の条件に置き換える。メール確認済み認証の条件を維持し、作成は整数の1、更新は現在値+1を要求する。未設定・フィールド削除・型不正・据え置きと、別ルールによる迂回を拒否する。
4. 保存拒否時に入力を失う画面を修正し、既存のエラー表示から編集を継続できるようにする。`permission-denied`を一律に競合扱いせず、原因判定用の追加取得・専用復旧フローは作らない。
5. Firestore Emulatorで同時更新・古い期待値・不正なバージョン・認証拒否・包括的許可による迂回をテストし、アプリ側で期待値の保持と失敗時の入力保持をテストする。

#### 3. 単独データと招待承認へ排他を適用する

1. メンバー編集・招待再発行・グループイベント編集にバージョン付き保存を適用する。単独データの削除とメンバー退避は、同じトランザクション内で期待バージョンを照合してから実行する。
2. メンバーイベントの固定IDへの保存で初回作成と更新を区別し、同時初回作成による上書きを拒否する。空メモの削除に期待値照合を追加し、既存の重複整理は保存成功後だけ実行する。
3. `AcceptInvitationUseCase`のメンバー紐付けと招待削除を、Infrastructure層の同一トランザクションへまとめる。同じ`inviteeId`の招待一覧を取得し、メンバーと全対象招待のID・期待バージョンを要求へ引き継ぐ。
4. 承認トランザクションでメンバーと全対象招待を読み取り・照合し、一致時だけ紐付けと全対象招待の削除を実行する。再試行でも対象・期待値を固定する（一覧取得後の新規招待の一意性保証は追加しない）。
5. 単独データの削除・退避の成功と競合拒否、照合後の同時更新による再試行、メンバーイベントの同時初回保存・空メモ削除・保存拒否後の重複整理抑止をテストする。
6. 招待承認の成功・同時承認・メンバー同時編集・招待再発行・対象削除・書き込み拒否で、紐付けと削除が一部だけ残らないことをテストする。同じ対象の招待2件はどちらのコードでも双方を削除し、別対象の招待は残ることも検証する。

#### 4. 旅行・グループ・DVCの親子保存へ排他を適用する

1. 旅行の作成・全体編集・場所・タスク・旅程の変更を、`trip_entries.version`の更新と同一バッチへまとめる。共有`FirestoreWriteContext`を使う経路にも適用する。
2. グループの作成・編集と既存の所属差分更新を、`groups.version`の更新と同一バッチで保護する。オンライン・オフラインとも、編集開始時の通常メンバーを比較元とする差分更新と、退避済みメンバーの既存所属の保持を維持する。
3. グループ退避トランザクションへ期待バージョン照合を追加する。メンバー退避で所属先グループを更新したり、所属差分更新でメンバーの退避状態を追加取得・照合したりしない。
4. DVC契約の作成・編集と、その契約のポイント利用・期間限定ポイントの追加・変更・削除を、`dvc_point_contracts.version`と同一の原子的な処理で保護する。契約一覧用の親や`groups.version`は使わない。
5. 旅行・DVC等の物理削除経路で、同じトランザクション内で親の期待値を照合してから親子を削除する。既存の子の全件置換・対象一覧取得を維持し、編集開始時の削除対象一覧の保持や一律の`Source.server`取得は追加しない。
6. 子の書き込みを親のバージョン更新と結び付けるRulesを`get()`・`getAfter()`で実装し、親更新のない書き込み・親参照の付け替えによる迂回を拒否する。親更新を伴う子の削除と、親自体の削除を区別する。
7. 親子の同時編集・異なる子の競合・子の追加変更削除・置換・直接更新拒否・親削除・退避・再試行・途中失敗をテストする。退避済みメンバーの所属保持、DVC契約の初回作成、グループ編集とDVC契約編集の独立性も検証する。

#### 5. 予定・個別回・ラベルへ排他を適用する

1. 予定の作成・編集・個別回の変更取消し・系列分割置換へ`calendar_events.version`を適用する。既存トランザクション・系列分割時の内容照合・ラベル参照件数調整を維持し、個別回だけの変更でも親を更新する。
2. 予定・個別回のRulesへ親バージョン更新との同時実行条件を追加し、予定削除トランザクションへ取得時の期待値照合を追加する。
3. ラベルの作成・編集・並べ替えへバージョンを適用し、並べ替えは一件でも競合すれば全体を拒否する。既存のラベル削除トランザクションにも期待値照合を追加する。
4. `eventCount`だけの内部更新では編集用バージョンを維持する。Rulesで変更フィールドを限定し、内部更新の許可から名前・色・順序・バージョンを変更できないようにする。
5. 予定・個別回・系列分割置換・削除・再試行の競合と原子性、ラベル編集・並べ替え・削除と内部件数更新をテストする。
6. 複数旅行・グループ・ラベルを含む保存のRules追加読み取り課金とアクセス回数を確認し、Emulatorで1操作10回・バッチとトランザクション全体20回の制限内の実行を検証する。原子性を失う分割は行わず、合意範囲を超える追加通信・複雑化が必要なら実装前にユーザーへ確認する。

#### 6. 既存データの初期化と切替を準備・実施する

1. 第2節のバージョン保持対象へ`version = 1`を設定する管理処理を作る。対象件数・不正値・完了状況を出力し、再実行で初期化済みの値を巻き戻さない。DVCは契約と子の紐付けが完了したデータを対象にする。
2. 初期化前の対象編集を利用不可にする。アプリで欠けたバージョンを補完せず、永続キャッシュは無効のままにする。
3. バックアップ、書き込み停止Rules、初期化、全件検証、厳格なRulesへの切替、失敗時の復旧手順を用意する。未初期化・初期化失敗が残る間は書き込みを再開しない。
4. Emulatorで移行前データ・初期化再実行・途中失敗からの復旧・停止中の拒否・初期化漏れ・切替後の保存成功と不正値拒否を検証する。旧アプリ用の互換処理・専用遮断・直接削除を識別するプロトコルは追加しない。
5. 対応アプリをキャッシュ無効で配布し、書き込み停止Rules適用→管理処理の実行→対象全件の検証→厳格なRulesへの切替を実施する。

#### 7. 永続キャッシュを有効化して検証する

1. 第1〜第6節の実装・検証・切替完了後に、`OnlineAppServices.initialize()`の`persistenceEnabled`を`true`へ変更する。容量と通常の取得処理はSDKの既定動作を維持する（編集開始時・保存前の再取得や親子の取得時点の混在検出は追加しない）。
2. 実SDKで再起動後のキャッシュ読取・保留書き込みの復旧・保存完了表示・古いキャッシュからの競合拒否を検証する。キャッシュ未取得データの取得失敗を空データ扱いする経路があれば修正する。
3. SQLiteのオフラインモードとAndroidウィジェットの既存動作を確認し、`./check.sh online`と`./check.sh offline`を実行する。

### 6. 本人のGoogleカレンダー連携（ストーリー25・オンラインのみ）

[ユーザーストーリー25](user_stories.md#25-オンラインモードのユーザーとして別のサービスで管理している自分の予定も一緒に確認したい予定の確認先を行き来したくないから)と[ER図](er_diagram.md)に沿い、以下の節・各節の番号順に実装・検証する。

#### 1. 連携設定の保存とモード別の依存を追加する

1. `google_calendar_connections`（`memberId`・`googleAccountId`）と`google_calendar_selections`（`memberId`・`calendarId`）のEntity・DTO・Mapper・Repositoryを追加する。設定はグループに紐付けず、表示対象は本人とカレンダーIDの組で一意に保存する。
2. Firestoreの保存・取得・削除処理とRulesを追加し、連携した本人だけが設定を読み書きできるようにする。
3. Composition Rootでオンライン用の依存を選択し、オフラインでは連携の入口を利用不可にする。連携設定はSQLite・バックアップ・復元の対象に追加しない。
4. 設定の保存・取得・削除、本人以外のアクセス拒否、オフラインでの連携処理の抑止をテストする。

#### 2. Google認証とカレンダー・予定の取得を追加する

1. Googleカレンダーの読み取り用の認証処理を追加する。認証情報の保存方法を選定して実装し、連携設定のEntity・DTO・Firestoreにはトークンや秘密情報を含めない。
2. 本人が利用できるカレンダーの一覧取得と、選択したカレンダーの表示期間内の予定取得を追加する。
3. 外部予定の本文・期間・終日区分・連携元カレンダー名を表示用データへ変換し、繰り返し予定の個別回の変更・取消しを反映する。`calendar_events`には保存せず、Googleカレンダーへの書き込み処理は追加しない。
4. 認証成功・失敗、カレンダー一覧と期間内予定の取得、繰り返し予定の変更・取消し、オフラインでのSDK初期化・通信の抑止をテストする。

#### 3. 表示対象の選択と共有予定への重ね合わせを追加する

1. Googleカレンダーへの連携操作と、表示対象カレンダーの選択・保存・再読込を行う画面とUseCase・Notifierを追加する。
2. 選択した外部予定をグループの予定と同じ日付に重ねて表示し、連携元のカレンダー名を付ける。外部予定とその繰り返し設定は読み取り専用で表示する。
3. 本人の外部予定をグループ切替後も表示し、他メンバーには公開しない。
4. 選択内容の保存・再読込、同じ日付への表示、取得元の識別、編集操作の抑止、本人だけへの表示、グループ切替後の継続表示をテストする。

#### 4. 再取得・エラー表示・再認証を追加する

1. 外部予定の取得状態をグループ予定と別に管理し、再取得操作でGoogleカレンダー側の変更を反映する。
2. 取得失敗の表示と再試行・再認証の操作を追加し、失敗時もグループの予定を表示する。
3. 再取得による変更反映、取得失敗中の共有予定表示、再試行と再認証による復旧をテストする。

#### 5. 連携解除を追加する

1. 本人の連携設定・表示対象を削除するUseCaseと解除操作を追加し、解除後は外部予定の表示を終了する。Googleカレンダーとグループの予定は削除しない。
2. 連携解除後に設定が削除されて外部予定が表示されず、Googleカレンダーとグループの予定が保持されることをテストする。
