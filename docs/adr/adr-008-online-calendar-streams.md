# ADR-008: グループのカレンダーはオンラインのみStreamで自動更新する

## ステータス

採用

## 決定日

2026-10-22

## コンテキスト

グループのカレンダーでは、他のメンバーや端末で変更された予定・色ラベルを、手動更新なしで確認したい。一方、オフラインモードは他の利用者とデータを共有せず、同じ自動更新方式を必要としない。

繰り返し予定と個別回は、[ADR-006](adr-006-atomic-aggregate-updates.md)で一つの集約として扱う。自動更新の導入にあたり、モード別の取得方式と、既存の競合検出・キャッシュ利用との関係を定める必要がある。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| 両モードで単発取得と手動更新を続ける | 不採用。他端末の変更が自動反映されない |
| オンラインのみStreamで監視し、オフラインは単発取得を維持する | 採用 |
| 両モードをStream化する | 不採用。共有を行わないオフラインにも監視の仕組みが必要になる |
| 親予定と個別回を独立した監視単位とする | 不採用。既存の集約単位に加えて監視結果の調整が必要になる |
| 親予定を変更検知の単位とし、個別回を含めて反映する | 採用。既存の集約更新の契約を利用できる |

## 決定事項

- アプリ内のグループ予定と色ラベルは、オンラインモードのみFirestoreのStreamによる自動更新を採用する。オフラインモードは単発取得と手動更新を維持する。Googleカレンダー連携はこの判断の対象外とする。
- 繰り返し予定は親予定を変更検知の単位とし、個別回を含む集約として表示へ反映する。個別回の独立した監視は行わない。
- 表示の自動更新と編集中の内容を分離し、[ADR-005](adr-005-version-based-concurrency-control.md)・ADR-006の編集開始時の期待バージョンと排他単位を維持する。
- 自動更新は監視・取得が成功する範囲で提供し、常時最新であることや複数の取得結果が同時点であることは保証しない。[ADR-007](adr-007-cached-read-consistency.md)の取得時点の混在許容を維持し、保存の成否と表示更新の成否は区別する。

## 決定理由

- 共有予定は他端末の変更を自動反映する利点が大きい。オフラインは既存の取得方式で必要な更新を扱えるため、モード間で方式を統一するための複雑性を増やさない。
- 変更検知を既存の集約単位に合わせることで、個別回の独立した監視と結果の調整を増やさずに済む。
- 自動更新で編集開始時の期待バージョンを差し替えると、古い入力による上書きを許すため、既存の競合検出を維持する。
- 自動更新を理由にキャッシュ利用や保存時の整合性方針を変更せず、通信・実装の複雑性の増加を抑える。

## 結果

- オンラインでは他端末の変更を自動反映できる一方、監視の維持と失敗時の復旧が必要になる。
- 変更受信や再接続により通信・読み取りが発生するため、通信量の削減自体は保証しない。
- 同じ繰り返し系列の異なる個別回の編集でも競合し得る。Stream化によって保存時の排他単位は変わらない。
- オンラインとオフラインで取得方式が異なるため、それぞれの更新動作を維持する必要がある。
