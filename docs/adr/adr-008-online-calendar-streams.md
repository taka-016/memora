# ADR-008: グループのカレンダーはオンラインのみStreamで自動更新する

## ステータス

採用（実装は未着手）

## 決定日

2026-10-22

## コンテキスト

グループのカレンダーは予定と色ラベルを単発取得し、画面表示時・手動更新時・保存後に再取得している。他のメンバーや端末での変更は再取得まで反映されず、保存後には変更していない予定も読み直す。

繰り返し予定の個別回の変更・取消しは親予定と別に保存されるが、[ADR-006](adr-006-atomic-aggregate-updates.md)により個別回の変更でも親予定のバージョンが更新される。オフラインモードはSQLite上の予定を管理し、他の利用者とは共有しない。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| 両モードで単発取得と手動更新を続ける | 不採用。他端末の変更が自動反映されない |
| オンラインのみStreamで監視し、オフラインは単発取得を維持する | 採用 |
| 両モードをStream化し、SQLiteにも変更通知を追加する | 不採用。オフラインで必要な更新は既存の再取得で扱える |
| オンラインで親予定と個別回をそれぞれ監視する | 不採用。独立した監視結果の結合・購読管理が増える |
| 親予定を監視し、変更された親の個別回だけ取得する | 採用。既存の集約更新の契約を利用できる |

## 決定事項

- アプリ内のグループ予定と色ラベルは、オンラインモードのみFirestoreのStreamで監視して自動更新する。対象カレンダーの利用中に監視し、取得範囲はグループ全件とする。Googleカレンダー連携は対象外とする。
- Application層に監視用QueryServiceインターフェースとUseCaseを設け、Firestoreによる実装とモード別の依存選択を外側の層へ置く。既存の単発取得は維持し、SQLiteの監視実装は追加しない。
- 個別回は独立して監視せず、初回取得と親予定の追加・変更に伴って取得する。変更のない親の個別回は再取得しない。個別回の変更時も親予定が更新される契約を前提とする。
- オンラインの通常の保存後は全件再取得せず、監視結果で表示を更新する。オフラインは画面表示時・保存後の再取得と手動更新ボタンを維持する。オンラインは通常の手動更新ボタンを表示せず、監視・取得エラー時に再試行操作を提供する。
- 自動更新でも選択日・表示月・編集中の入力・編集開始時の期待バージョンを保持する。[ADR-005](adr-005-version-based-concurrency-control.md)とADR-006の楽観的排他を維持し、同一予定・同一繰り返し系列の競合を拒否する。カレンダー全体のバージョン管理には変更しない。
- 予定と色ラベルの取得エラーを区別し、表示後のエラーでは直前の表示を保持する。保存の成否と表示更新の成否は分ける。一時的な通信断はSDKのキャッシュ・再接続に任せ、監視が終了した場合や個別回の取得・変換に失敗した場合は再試行で復旧できるようにする。
- 自動反映は監視・取得が成功する範囲で提供する。通信断や複数の取得結果の間で同時点の表示は保証しない。[ADR-007](adr-007-cached-read-consistency.md)の取得時点の混在を許容し、時点をそろえる専用の検証・再取得は追加しない。

## 決定理由

- オンラインの共有予定は他端末の変更を自動反映する利点がある。オフラインの取得方式まで変更せず、共有機能に必要な範囲へ実装を限定する。
- 親予定の更新を変更通知として利用すれば、個別回の独立した監視を増やさず、変更のない予定の個別回の読み直しも抑えられる。
- 自動更新で編集開始時の期待バージョンを差し替えると、古い入力による上書きを許すため、既存の競合検出を維持する。
- キャッシュ利用や取得失敗を伴うため即時・同時点の表示を保証せず、既存の整合性水準と通信・実装の複雑性を維持する。

## 結果

- オンラインでは他端末の変更が手動更新なしで反映され、通常保存後の全件再取得を省ける。初回のグループ全件取得は残り、他端末の変更受信や再接続により通信・読み取りが発生するため、通信量の削減自体は保証しない。
- 監視の共有・解除、取得結果の前後逆転への対処、部分的な取得失敗と再試行、楽観的なラベル並べ替えと受信結果の調整が必要になる。
- 同じ繰り返し系列の異なる個別回の編集でも競合し得る。Stream化によって保存時の排他単位は変わらない。
- オフラインのDB・保存形式・更新通知には変更を加えない。
