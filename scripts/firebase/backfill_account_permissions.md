# オンライン認可の補完と切替

このコマンドは認可文書とメンバーの所属一覧を生成・照合し、所属・招待の文書IDをルールから直接参照できる形式に移し、タスクの保存先も親旅行から補完します。アプリの配布・ルールのデプロイは行いません。オフラインのDB・バックアップは変更しません。

## 切替手順

1. 旧版アプリ・バックグラウンド更新・他の管理操作を停止し、Firestoreをバックアップします。読み取り開始から補完・照合の終了まで元データを変更しない運用が前提です。
2. `just setup-cloud indexes`で`firestore.indexes.json`をデプロイし、構築完了を待ちます。旅程ウィジェットには`itinerary_items`の`groupId ASC・tripId ASC・startDateTime ASC`と末尾が`DESC`の2本を追加しています。旅行内の並び替えにも`groupId・tripId・並び順/日時`のインデックスを追加しています。DVCは既存の`groupId・contractId・日時`のインデックスを使います。所属・招待・認可の文書IDによる照合には複合インデックスは不要です。
3. 対象プロジェクトの読み書き権限を持つOAuthアクセストークンを`FIRESTORE_ACCESS_TOKEN`に設定し、確認コマンドを実行します。

```bash
dart run scripts/firebase/backfill_account_permissions.dart <projectId> <report.json>
```

4. レポートの`documents`・`memberDocuments`・`issues`・`writeUnits`・`retainedTaskIds`を確認します。本人の重複対応、所属の重複、所有者の所属不足、既存認可・メンバーの所属一覧との不一致は自動修正せず、適用を拒否します。所属参照IDの区切り文字`:`を含む既存のグループ・メンバーIDも報告します。削除済み親への残存所属は権限に含めません。
5. 不整合を解消して確認をやり直した後、同じ指定へ`--apply`を付けて適用します。

```bash
dart run scripts/firebase/backfill_account_permissions.dart <projectId> <report.json> --apply
```

6. 同じ確認コマンドを再実行し、不一致がなく`writeUnits`が0になることを確認します。`member_events.groupId`は、このコマンドでは推測・補完しません。保存先グループを手動で補完し、未補完の記録がないことを確認してください。既存データの削除・再作成で補完を代替しません。
7. 新版アプリを配布し、`just setup-cloud rules`でルールを切り替えてから利用を再開します。旧版の所属保存・招待コード検索は新ルールで拒否されるため、旧版の利用を再開しないでください。補完前に新ルールへ切り替えると正当な取得・保存が失敗し、認可文書のない既存アカウントも未登録と判定されます。必ず補完を完了してから切り替えてください。

レポートにはメンバー・グループ・アカウントのIDと、招待コードを含む文書パスが入ります。バックアップと同様に管理してください。

## 補完対象と再開

| 対象 | 補完内容 |
| --- | --- |
| `account_permissions/{UID}` | 本人の`memberId`、所属の`memberGroupIds`、所有者・管理者の`managedGroupIds`。未作成の文書だけを作成する |
| `members/{memberId}` | オンライン専用の`groupIds`・`managedGroupIds`。補完時はプロフィールの`version`を1進める |
| `group_members/{groupId}:{memberId}` | 有効な所属の既存フィールドを維持して文書IDを移す。削除済み親への残存所属は保持する |
| `tasks.groupId` | 親旅行の保存先を補完し、同じ保存単位で親の`version`を1進める。既存の保存先が親と異なる場合は適用せず報告する |
| `member_invitations/{invitationCode}` | 既存のコード・バージョン・発行日時を維持して文書IDを移す |

1つの保存単位は1書き込み、文書IDの移動は作成・削除の2書き込みを同じコミットで行います。既存文書の更新・削除には取得時の`updateTime`、新規作成には`exists: false`を条件として付けます。タスクの補完は旅行ごとに対象の全タスクと親バージョンを同じコミットに含めるため、この単位は2書き込みを超える場合があります。親のないタスクは推測せず保持し、`retainedTaskIds`へ報告します。未補完の子はルールで拒否し、別グループで親IDを再利用しても公開しません。全データをまとめた原子性や、元データ全体の同一時点取得は保証しません。

失敗・結果不明の場合は、レポートの`appliedDocuments`・`pendingDocuments`とFirestoreを照合し、確認からやり直してください。適用済みで一致する認可・所属一覧・参照IDは再保存しません。移動先の作成と移動元の削除は同じ保存単位なので、途中で片方だけ確定しません。

## 保存時の更新数と上限

通常の所属管理では、グループの期待バージョンと、変更対象メンバーの現在の所属一覧をトランザクション内で取得します。別グループの同時変更は再試行で取り込み、対象グループの期待バージョンは編集開始時の値を維持します。DVC・場所・旅程のグループ単位の取得は親一覧を取得して親IDごとに問い合わせるため、親数に応じてリクエストが増えます。タスク・旅程の単独取得では、先に親旅行から保存先を取得します。グループ削除では認可解除対象の所属をサーバーから取得し、親のバージョンで競合を検出します。

- 変更する所属文書数を`M`、所属・管理対象の一覧が変わるメンバー数を`P`、そのうちアカウント連携済みの人数を`A`とすると、グループ編集の書き込みは最大`1 + M + P + A`件です。色・並び順だけの変更では、メンバーと認可文書を更新しません。
- `N`人のグループ作成は最大`1 + 2N + A`件です。作成者も人数に含みます。
- グループ削除は親の退避・削除に加えて、所属一覧と認可の解除で最大`2 + P + A`件です。所属文書と関連記録は削除しません。
- ルールは本人の認可・本人メンバー・対象グループと、変更対象の保存前後のメンバー・所属・認可を参照します。同一参照のキャッシュを前提とした保守的な見積りは、共通参照を最大6回、連携済みの参照対象1人につき最大4回、未連携の参照対象1人につき最大2回です。ここでの対象には、所属一覧が変わる人数`P`だけでなく、色・並び順だけを変更する所属も含めます。例えば連携済み3人と未連携1人で20回です。色変更だけなど、実際の参照数が少ない操作もあります。
- Firestoreのルール評価には、各操作10参照、トランザクション・バッチ全体20参照の上限があります。人数だけの固定上限ではなく、変更対象・役割・保存内容によって保存できる範囲が変わります。超過時は保存全体が失敗し、原子的な更新を分割して成功扱いにする処理は行いません。[ルールの制限](https://firebase.google.com/docs/rules/rules-behavior)
- 文書は最大1 MiB、APIリクエストは最大10 MiB、トランザクションは最大270秒・アイドル60秒です。所属一覧も文書サイズに含まれます。また1文書のインデックスエントリは最大40,000件です。[Firestoreの上限](https://firebase.google.com/docs/firestore/quotas)

Firestore Emulatorで確認する場合は、`FIRESTORE_EMULATOR_HOST`を指定して`tools/ci/firestore_*_rules_test.mjs`をそれぞれNode.jsで実行します。Emulatorによる成功を、本番のサイズ・参照上限を超えて保存できる保証には使いません。
