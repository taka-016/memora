## 起動時の保存済みアプリモード確認を廃止する

オンライン・オフラインはapplication IDと保存領域が異なる別APKのため、モードはビルド設定を正とする。

1. ウィジェット・予定通知のバックグラウンド処理と定期タスク登録を、保存済みモードではなくビルド設定からモードを取得する形へ変更する。
2. `app_bootstrap.dart`の保存済みモードの読み込み・比較・保存と、モード変更に伴うウィジェットキャッシュの削除・再描画を廃止し、不要になった`SharedPreferencesAppModeStorage`を削除する。他の契機によるキャッシュ削除・更新は維持する。

## 起動時の認証トークン強制更新を廃止する

[ADR-010](adr/adr-010-sdk-managed-auth-token-refresh.md)に従う。

- `AuthNotifier`の起動時認証から`getIdToken(true)`による強制更新の待機を取り除き、有効なトークンの再利用と期限に応じた更新をFirebase SDKの通常のトークン管理に任せる。認証状態の監視と本人メンバーの確認は維持する。
- 強制更新の廃止によって不要になるUseCase・Serviceのメソッド・Providerと、強制更新専用の再試行処理を整理する。本人メンバー取得など、残る起動時認証の失敗・再試行の扱いは維持する。

## アプリ起動時の共通データをキャッシュで表示し、裏で最新情報を取得する

1. オンライン版の所属グループ一覧・色ラベルをアカウントごとに端末へ保存し、アプリ終了後の起動でも再利用できるようにする。アプリ共通の状態として取得済み情報と最新確認の状態を共有する。既定グループ・予定時間・通知設定は既存の端末保存を利用し、別アカウントのキャッシュを表示しない。
2. 通常起動・ウィジェット起動を問わず、アプリ起動時の共通処理で認証後にキャッシュを復元し、利用画面の表示・入力を開始できるようにする。最新情報は裏で取得して共通状態とキャッシュへ反映し、各画面の入力中の内容を保持する。キャッシュがない情報だけ初回取得を待ち、予定追加への遷移や特定画面を開くことを共通キャッシュ利用の開始条件にしない。
3. 予定追加の保存時は最新確認済みの情報で保存先グループ・選択ラベルの有効性を判断する。確認が未完了なら進行中の取得を待ち、未開始・失敗の場合は取得してから保存する。確認済みなら保存のためだけに再取得しない。
4. 最新確認に失敗した場合は予定追加画面を閉じずにエラーを表示し、入力を残して再度保存を試せる状態へ戻す。保存先やラベルが無効なら再選択を促す。アプリ終了後の下書き保持は対象外とする。

## 検討保留（実装タスクとは別枠・方針未決定）

この節は、実装できる粒度に達していない検討事項と調査結果の保管先とする。既存の実装タスクとは区別し、ユーザーが方針を決めるまで実装に着手しない。

### カレンダーの永続キャッシュによる通信量削減

- Firestoreの永続キャッシュは既に有効で、プロセス終了後のキャッシュ利用も実測で確認済み。独自の月別キャッシュ・購読の保持範囲は[ADR-009](adr/adr-009-calendar-month-subscription-cache.md)を参照する。
- 月別キャッシュの永続化によって再起動後の購読・再取得の通信量を削減できるか、更新・失効の扱いと合わせて検討する。通信量の削減が見込める方式を確認できた場合に実装対象とする。

### Firestoreの読み取り削減の追加候補（優先度5以降）

年表・旅行は現在少量だが、全履歴取得と広範囲の再取得を続けると蓄積に比例して読み取りが増える。以下は対応未決定の検討事項とする。

- **5. 年表の全年取得・広範囲の再取得**: グループと各メンバーのメモは全年分、旅行は初期状態で前後5年の計11年分を問い合わせる。復帰時の1分間隔の抑制を超えた更新や旅行保存時のProvider全体の無効化で再取得が増える。表示・追加表示する期間への限定と、変更したメンバー・グループ・年だけの更新を検討する。
- **6. グループID取得のための全メンバー取得**: 通知の所属ID取得でも画面用の全メンバー付きグループ取得を使う。認可文書のIDだけを取得する経路と、画面間の取得済みデータの共有を検討する。
- **7. 地図の全旅行・全地点取得**: グループ選択時と旅行変更後に全履歴を取得する。取得済みデータの部分更新、期間・地図範囲に応じた段階取得を、全履歴を一度に表示する仕様との兼ね合いで検討する。
- **8. 旅行保存時の全子データ取得・再作成**: タイトルだけの変更でも全場所・全タスク・全旅程を取得し、削除・再作成する。基本情報と子データの変更の分離を、既存の競合検出・一括保存を維持する範囲で検討する。
- **9. DVCの全履歴取得**: 計算画面は全契約・限定ポイント・利用履歴、年表は全利用履歴を取得する。過去の利用が現在の残高へ影響するため、必要期間と繰越情報の扱いを決めてから取得範囲の限定を検討する。
- **期間クエリのインデックス読み取り（影響未計測）**: カレンダーの開始・終了日時の2項目に範囲条件があり、返却文書以外の読み取りも増える可能性がある。Query Explainで走査量を確認してから、クエリ・インデックスの変更要否を判断する。

### アプリ識別子と既存インストールの扱い

- **推奨候補（未決定）**: オンライン版を`io.github.taka016.memora`、オフライン版を`io.github.taka016.memora.offline`とする案。GitHub名`taka-016`からハイフンを除いて利用者名に由来する識別子とし、アプリの表示名とは分ける。利用先での識別子の重複は採用前に確認する。保有する独自ドメインがある場合は、その逆順を接頭辞にする案も比較する。
- **既存インストール**: application ID変更後はAndroid上で別アプリとなり、旧版のSQLite・端末設定・ログイン状態・端末カレンダーの表示設定・ホーム画面ウィジェットは自動では引き継がれない。旧版の併存・削除時期と、必要なデータ引継ぎの範囲を決める。オフラインデータを残す場合は現行形式のバックアップの手動復元を候補とし、旧形式互換や自動移行を追加する前提にしない。
