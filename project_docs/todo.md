## 全機能のFirestore読み取り回帰をエミュレータで自動判定する

目的は、各変更で不要な読み取りが増えていないことを継続的に保証すること。本番の課金読み取り数との一致・課金額推定・Query Explainの導入は完了条件に含めない。オンライン版の実装とFirestore SDKをAndroidエミュレータ上で動かし、Firestore／Auth Emulatorへ接続する。SQLite・FirestoreのFake・Repositoryのモックでは代替しない。[ADR-009](adr/adr-009-calendar-month-subscription-cache.md)の既存の購読回数テストは残し、全機能を通す回帰検出を追加する。読み取り削減の実装や整合性保証の強化は、この基盤追加へ混在させない。

以下を依存順に実装する。

1. **テスト専用の起動・接続構成を用意する。** `integration_test/firestore_read_regression/`に実端末向けのテスト入口を追加し、オンライン版の起動、認証、Firestore接続、固定時刻をテスト用に指定できるようにする。アプリ起動前に接続先を設定し、通知・ウィジェットの別isolate／別ProviderContainerでの初期化にも同じ設定を渡す。Singletonの直接参照を含め、全Firestoreアクセスが同じテスト用プロジェクトへ向く構成にする。Git管理外の`firebase.json`を変更・強制追加せず、Git管理する専用Emulator設定と`demo-memora-read-regression`を使用する。本番用の採番・利用停止設定の更新や外部サービスへの接続を行わずにテストを起動できるようにする。
2. **データ・シナリオ設定・予算をコードから分離する。** `test/fixtures/firestore_read_regression/`に`datasets/*.json`、`scenarios/*.json`、`budgets/*.json`を配置する。データファイルには認証アカウント、コレクション・文書ID・フィールド、日時・参照、端末設定、ウィジェット配置、通知権限を記載する。シナリオ設定には使用データ、固定時刻・タイムゾーン、操作パラメータ、キャッシュ条件、期待結果、予算IDを記載する。予算には操作・取得対象別の上限とデータ件数からの算出根拠を持たせる。同じ操作のデータ内容・件数・期間・予算はJSONだけで変更可能にし、Dart・Kotlin・シェルへ文書や件数を重複埋め込みしない。日時等の型付き値を復元するローダー、入力形式・参照・予算対応の検査、投入処理を追加し、不正な入力は開始前に失敗させる。同じJSONをホスト側の投入処理と端末側のシナリオ実行で利用できるよう、テスト用assetへの同梱または実行時転送を組み込む。
3. **基準データと派生データを用意する。** 基準時刻は`2026-11-15T12:00:00+09:00`、タイムゾーンは`Asia/Tokyo`とする。基本セットは1グループ・4メンバーと対応する所属／認可文書、色ラベル2件、当月と前後2か月の各月中旬に単発予定10件ずつとする。年表用に2021〜2031年の各年にグループメモ1件・各メンバーのメモ1件、旅行2件、各旅行に場所3件・タスク4件・旅程6件を用意する。DVCは契約2件と各契約の限定ポイント2件・利用履歴12件を用意する。起動に必要な`app_settings/availability`も含める。空データ、複数グループ、別アカウント、招待、期間外の大量データ、繰り返し・取消・終日・月年境界は派生セットとして分離し、対象内件数を変えず対象外件数だけ増やせるようにする。展開・投入した文書数をコレクション別に出力する。
4. **実SDKへの読み取りを操作単位で計測する。** QueryServiceだけでなくRepository、トランザクション、起動共通データ、利用可否確認、通知、両ウィジェット、Singleton直接参照を含む読み取り箇所を列挙し、SDK境界にテスト用の計測を接続する。単発取得の開始回数・返却文書数、購読開始回数・初回文書数・変更差分数を取得対象別・操作別に記録する。キャッシュ受信、ローカル書き込みの反映、サーバー受信、同一購読の再通知を区別し、毎回の`QuerySnapshot.docs.length`の単純加算で更新のたびに全件を数えない。計測のために永続キャッシュを無効化したり取得元をサーバーへ強制したりせず、通常の取得方式を維持する。別isolate／プロセスからも実行ID・操作ID付きで結果を集約し、計測漏れ・取得エラーを0回として扱わない。データ投入・別クライアントの更新準備・期待結果照合のための読み出しはアプリの計測から除外し、それらによってアプリへ届く変更受信は含める。これらの観測値を品質指標とし、SDK内部の再接続回数や課金読み取り数へ換算しない。

6. **状態を再現できるシナリオ実行器を追加する。** シナリオごとにFirestore／Auth、端末の設定・通知予約・ウィジェット状態を初期化し、キャッシュなしの初回起動、永続キャッシュありの再起動、同一プロセス内の再表示を区別する。固定した`AppClock`と明示的な処理完了条件で操作を進め、起動時取得と操作時の追加取得を分けて記録する。画面・通知・ウィジェットの必要な非同期処理と計測の集約が完了してから区間を閉じ、操作直後に遅れて発生する追加取得を取りこぼさない。取得回数の上限だけでなく期待する表示・保存・通知予約・ウィジェット内容も同時に判定し、失敗・タイムアウト・未実行の操作では合格させない。

## 検討保留（実装タスクとは別枠・方針未決定）

この節は、実装できる粒度に達していない検討事項と調査結果の保管先とする。既存の実装タスクとは区別し、ユーザーが方針を決めるまで実装に着手しない。

### カレンダーの永続キャッシュによる通信量削減

- Firestoreの永続キャッシュは既に有効で、プロセス終了後のキャッシュ利用も実測で確認済み。独自の月別キャッシュ・購読の保持範囲は[ADR-009](adr/adr-009-calendar-month-subscription-cache.md)を参照する。
- 月別キャッシュの永続化によって再起動後の購読・再取得の通信量を削減できるか、更新・失効の扱いと合わせて検討する。通信量の削減が見込める方式を確認できた場合に実装対象とする。

### Firestoreの読み取り削減の追加候補（優先度5以降）

年表・旅行は現在少量だが、全履歴取得と広範囲の再取得を続けると蓄積に比例して読み取りが増える。以下は対応未決定の検討事項とする。

- **5. 年表の全年取得・広範囲の再取得**: グループと各メンバーのメモは全年分、旅行は初期状態で前後5年の計11年分を問い合わせる。復帰時の1分間隔の抑制を超えた更新や旅行保存時のProvider全体の無効化で再取得が増える。表示・追加表示する期間への限定と、変更したメンバー・グループ・年だけの更新を検討する。
- **6. グループID取得のための全メンバー取得**: 通知の所属ID取得でも画面用の全メンバー付きグループ取得を使う。認可文書のIDだけを取得する経路と、画面間の取得済みデータの共有を検討する。
- **7. 地図の全旅行・全地点取得**: グループ選択時と旅行変更後に全履歴を取得する。取得済みデータの部分更新、期間・地図範囲に応じた段階取得を、全履歴を一度に表示する仕様との兼ね合いで検討する。
- **8. 旅行保存時の全子データ取得・再作成**: タイトルだけの変更でも全場所・全タスク・全旅程を取得し、削除・再作成する。基本情報と子データの変更の分離を、既存の競合検出・一括保存を維持する範囲で検討する。
- **9. DVCの全履歴取得**: 計算画面は全契約・限定ポイント・利用履歴、年表は全利用履歴を取得する。過去の利用が現在の残高へ影響するため、必要期間と繰越情報の扱いを決めてから取得範囲の限定を検討する。
- **期間クエリのインデックス読み取り（影響未計測）**: カレンダーの開始・終了日時の2項目に範囲条件があり、返却文書以外の読み取りも増える可能性がある。Query Explainで走査量を確認してから、クエリ・インデックスの変更要否を判断する。

### アプリ識別子と既存インストールの扱い

- **推奨候補（未決定）**: オンライン版を`io.github.taka016.memora`、オフライン版を`io.github.taka016.memora.offline`とする案。GitHub名`taka-016`からハイフンを除いて利用者名に由来する識別子とし、アプリの表示名とは分ける。利用先での識別子の重複は採用前に確認する。保有する独自ドメインがある場合は、その逆順を接頭辞にする案も比較する。
- **既存インストール**: application ID変更後はAndroid上で別アプリとなり、旧版のSQLite・端末設定・ログイン状態・端末カレンダーの表示設定・ホーム画面ウィジェットは自動では引き継がれない。旧版の併存・削除時期と、必要なデータ引継ぎの範囲を決める。オフラインデータを残す場合は現行形式のバックアップの手動復元を候補とし、旧形式互換や自動移行を追加する前提にしない。
