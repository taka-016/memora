# ToDo List

## 個人用グループで予定・年表を管理する

[ユーザーストーリー23・24・26](user_stories.md#23-ユーザーとして家族や友人の予定を記録し日付ごとにまとめて把握したい互いの予定を見落とさず調整したいから)に対応する。個人用グループは自分だけが所属する通常のグループとして手動作成し、年表は既存のグループ単位の選択を維持する。

以下は全体方針の確認対象となる未実装の作業。依存関係に沿って、利用者の操作を一通り完成させられる5つのまとまりで対応する。認可コレクションとメンバー別イベントのグループ単位化は[ER図](er_diagram.md)を参照。

### 1. メンバー別イベントをグループごとに管理できるようにする

- メンバー別イベントのEntity・DTO・UseCase・取得・保存・年表の表示に必須の`groupId`を追加し、`groupId`・`memberId`・`year`の組ごとに記録を管理する。同じメンバー・同じ年でも別グループの内容を表示・上書き・削除しない。
- Firestoreの保存先の識別・取得条件・重複整理と、SQLiteのスキーマ・取得・保存、現行形式のバックアップをそろえる。オフラインの旧スキーマ・旧バックアップ向けの互換処理や自動再作成は追加しない。
- 既存オンラインデータへ`groupId`を設定する移行スクリプトを追加する。イベントIDと移行先グループIDの明示的な対応を入力とし、推測や全グループへの自動複製は行わない。未指定・移行先不明・同じグループ／メンバー／年への重複を報告する。
- スクリプトは書き込み前に対象と変更内容を確認できるようにし、既存のイベントIDと記録内容を保持して未設定の`groupId`だけを補完する。取得後の変更や既存の`groupId`を上書きせず、再実行時は補完済みと競合を区別する。認可導入と合わせ、旧版から未補完データが増えることを防ぐ導入手順を用意する。

### 2. 所属外からのアクセスと不正な権限変更をオンラインで拒否する

- UIDを文書IDとする`account_permissions`へ、本人の`memberId`、所属先の`memberGroupIds`、所有者・管理者の`managedGroupIds`を保持する。管理対象は所属先の一部とする。`AuthenticatedCurrentMemberResolver`、本人・グループのQueryServiceとマッパーを接続し、本人の取得・所属一覧・詳細で共通の認可参照を使う。メンバー情報へ認可用の所属一覧を追加せず、画面から渡された本人IDや管理者フラグを権限の根拠にしない。
- グループ作成・編集・所属追加／解除・管理者変更と、対象アカウントの認可情報を同じバッチまたはトランザクションで保存する。作成者は所有者かつ所属メンバーにする。管理者でも認可文書だけの更新は拒否し、変更前の対象グループの管理権限と保存後の所属・役割との一致を、所属側・認可側の両方で要求する。別グループの所属・権限や本人の対応を変更させず、自己昇格と別グループの同時編集による上書きを防ぐ。
- 本人登録はメンバーと空の認可文書の作成をまとめ、招待受理は有効な招待を根拠に`accountId`の紐付け・既存所属の認可情報・受理済み招待の削除を同じトランザクションへ含める。本人登録・グループ作成・招待受理を管理者による通常更新と分け、既存の招待の有効性・競合検出を維持する。グループ・メンバー削除は親の退避と関連データの保持を維持し、削除済み親や残存所属を権限の根拠にしない。
- FirestoreのQueryService・Streamと、通知・ウィジェットのバックグラウンド取得を、本人・所属グループ・親IDに限定する。メンバー・所属・招待と関連する場所・タスク・旅程・個別回・DVCデータを含め、取得後のフィルターや別の汎用ルールから認可を回避できないようにする。認可文書は本人の単一文書取得を許可し、他人の認可文書や全アカウントの認可一覧を公開せずに権限更新を行えるようにする。
- Firestoreルールで、グループ・所属・管理者・任意ラベルの管理は所有者・管理者に、予定・個別回・年表の記録と関連データの編集は所属メンバー全員に許可する。ラベルの`eventCount`更新を定義編集と区別し、予定の移動には変更前後の両グループへの所属を必要とする。既存のバージョン検出・集約保存条件を維持し、単体取得・一覧・Streamで同じ範囲を保証する。所属解除後のサーバー取得を拒否し、取得済みデータの回収・消去は保証に含めない。オフラインへFirestoreルールを適用しない。
- 既存アカウント・メンバー・所属・管理者設定から認可文書を生成・照合する補完スクリプトを用意し、重複対応・不一致を報告する。補完内容を確認し、メンバー別イベントの移行とそろえてルールを切り替える。未補完データは削除・再作成しない。所属文書をルールから直接照合する保存形式、必要なインデックス、参照回数、対象アカウント数に応じた追加更新数と保存上限を具体化する。所属・役割と認可情報の原子的な更新を超える整合性保証を追加する場合は、影響を説明して判断を仰ぐ。

### 3. カレンダーで複数グループを選択してまとめて確認できるようにする

- Application層の設定モデル・StorageとSharedPreferences実装を追加し、複数の表示グループIDと単一または未設定の予定追加時の既定グループを独立して保存する。初期値は空・未設定とし、所属が1つでも自動選択しない。オンラインはアカウント、オフラインは端末内利用者ごとに分離し、UIとバックグラウンドで同じ保存口を使う。既存の週開始・六曜設定、年表選択、旅程ウィジェットの単一グループ設定と混同せず、引き継ぎや別端末への同期をしない。
- Riverpodコード生成の設定Notifierと不変Stateで、利用者ごとの読み込み・所属との照合・保存・失敗・再試行を管理する。所属取得成功時だけ削除・脱退したグループを利用対象から外し、取得失敗で保存済み選択を消さない。保存失敗時は確定済み値を維持し、利用者切替前の非同期結果を反映させない。設定画面に既定グループの入力を追加し、非表示の所属グループと「未設定」を選択できるようにする。既定値の変更で表示選択を変えず、所属取得失敗時は候補を確定しない。
- 既存の`CalendarNotifier(groupId)`を利用して選択グループの予定・ラベル・取得状態をまとめるNotifierと不変Stateを追加する。選択日・表示月を共有し、追加したグループだけ取得・監視する。解除・利用者切替・画面破棄で不要な監視と遅れて届く結果を除外する。一部の取得失敗でも他グループの取得済みデータを維持し、失敗対象と再試行を表現する。オンラインのStream更新、オフラインの保存後再取得・手動更新を維持する。
- 月・週レイアウト、日別一覧、`calendar_display_labels.dart`、端末カレンダー重ね合わせを統合状態に対応させる。描画用ラベルはグループIDを含めて区別し、DBのラベル種別・メンバーID・任意ラベルIDへ表示用識別子を混ぜない。繰り返しの回はグループ・予定ID・元の開始日時で識別する。表示グループが空でも、設定済みの端末予定と祝日・六曜を表示し、端末予定の識別・読み取り専用表示を維持する。
- カレンダーのルート・入口から必須の単一`groupId`、所属1件時の自動選択、グループ一覧への戻り操作を外す。所属グループを右上のダイアログで複数選択し、確定・キャンセル・全解除を扱う。未設定時は表示設定への案内を出し、月移動・週表示・日別一覧・スワイプを共通の選択日に追従させる。予定詳細に保存先グループ名を表示する。
- 任意ラベル管理をカレンダーの表示状態から独立したNotifierとStateへ分離し、既存グループの編集画面から開けるようにする。カレンダー側の入口を削除し、所有者・管理者だけが管理できるようUIと保存側をそろえる。名前・背景色・文字色・並び順・使用中ラベルの削除拒否を維持し、固定ラベルを任意ラベル一覧へ混ぜない。一般メンバーも予定入力で登録済みラベルを選べるようにする。

### 4. 予定の保存先を選択し、別グループへ移動できるようにする

- `CalendarEventDialog`の単一グループ固定を入力状態へ変更し、新規は開いた時点の既定グループ、編集は保存済みグループで初期化する。非表示の所属グループも候補にし、設定変更で入力中や保存済みの値を上書きしない。グループ未選択ではラベル選択・保存を不可にし、所属なしなら作成・参加を案内する。
- グループ切替時はメンバー・任意ラベルを取得し、選択ラベルを変更先の「グループの予定」へ戻す。元のグループへ戻っても以前のラベルを復元せず、切替前の非同期結果を反映させない。取得失敗でも入力を保持して再試行できるようにする。グループを変えない編集では所属解除・削除済みメンバーのラベル参照を維持し、グループ切替だけで日時・タイトル・詳細・通知を変えない。
- Application層に移動UseCaseとRepositoryの保存契約を追加し、登録・同一グループ内編集・通常予定の移動・系列全体の移動を区別する。変更前後の所属と編集開始時の予定・系列・期待バージョンを確認し、予定IDを維持する。個別回から開いた場合も移動は系列全体だけを扱い、個別回・以降の分割処理へ渡さない。系列と全個別回のラベルを変更先の「グループの予定」へ戻し、繰り返し条件・日時・タイトル・URL・メモ・場所・通知の個別変更と取消しを保持する。
- FirestoreとSQLiteで、親予定と個別回の`groupId`・ラベル参照を同じトランザクション内で移す。別予定の作成と元予定の削除へ分割しない。変更先のラベル参照確認と変更前後の任意ラベルの`eventCount`調整を行い、ID・元の開始日時・取消しを維持する。失敗・競合時は移動前のデータを保持し、既存の競合エラーとして再入力・再読み込みへ戻す。オフラインの旧形式互換は追加しない。
- 保存前に変更先との共有、系列全体の移動とラベル変更、非表示グループへの保存で表示から外れることを確認できるようにする。失敗時は入力を保持し、キャンセルでは保存しない。保存後はMutationCoordinatorで変更前後の予定再取得・通知再予約・ウィジェット更新を調整する。表示選択・既定グループを自動変更せず、オンラインの自動受信でも編集中の入力・競合判定の基準を上書きしない。

### 5. ウィジェット・通知・復元後の表示をグループ横断カレンダーへそろえる

- ウィジェットの予定取得・繰り返し展開・月／日別キャッシュを共通の表示設定に対応させる。元グループ・予定・個別回の識別を保持し、各グループの固定ラベル色・文字色を解決する。キャッシュの読み込み状態とマージを利用者・表示対象で区別し、選択解除前や利用者切替前の内容を再表示させない。未選択でも日付・祝日・六曜を含むキャッシュを作り、端末予定を重ねられるようにする。既存のキャッシュ月数とファイル公開の扱いは維持する。
- Androidの月・日別ウィジェットと端末カレンダー重ね合わせを新キャッシュへ対応させる。予定クリックは元グループ・予定・個別回を渡し、日付・追加クリックは保存先を固定せず日付と追加要求を渡す。Provider・バックグラウンドcomposition root・更新処理も共通設定を使い、旅程用グループが未設定でもカレンダー更新を行う。表示設定・端末カレンダー設定・予定の保存／移動／削除・所属変更・ログアウトで更新し、旅程用の対象と更新間隔、既存キューの直列実行・失敗回復を維持する。設定画面の単一グループ入力は旅程用と明示する。
- 通知の取得・監視は表示選択から独立させ、オンライン・オフラインとも現在の利用者の有効な所属グループを対象にする。予定・個別回の通知設定、通知利用設定、OS権限に従い、表示選択の解除だけでは予約を消さない。所属解除・グループ削除・予定移動・通知設定変更では所属内の最新予定から再予約する。
- ウィジェット・通知からの起動は、共通表示設定の読み込み後に日付・予定・個別回の要求を解決する。追加要求はアプリ内と同じ既定グループで初期化し、URIの元グループで上書きしない。通知先が所属内でも非表示ならその旨を案内し、表示対象へ自動追加したり対象予定だけを特別表示したりしない。
- 新しい表示・既定グループ設定はSQLiteスナップショット・`OfflineBackupSnapshot`へ含めず、復元処理でも端末設定を書き換えない。復元後は設定Notifierで読み直し、利用者・有効な所属・端末の設定から月／日別キャッシュを再構築する。所属外・存在しないIDは利用対象から外し、復元データのグループを初期選択しない。旅程用グループに依存した既存の復元後カレンダー更新を分離する。

## `com.example`から正式なアプリ識別子への変更

着手前に「検討保留」の[識別子と既存インストールの扱い](#アプリ識別子と既存インストールの扱い)を確定する。オンライン・オフラインの別アプリ構成を維持し、オフライン版へFirebase・Google APIの設定や連携機能を追加しない。

1. 下表に従い、新しいオンライン版の識別子に対応するFirebase・Google Cloudのアプリ登録と認証設定を用意する。同じプロジェクトのAuthentication・Firestoreデータを引き続き使い、プロジェクトや既存データを作り直さない。
2. `android/app/build.gradle.kts`の`applicationId`・`namespace`と、`android/app/src/main/kotlin/com/example/memora/`配下のパッケージ宣言・配置を新しい名前へ変更する。オフライン版の`.offline`サフィックスを維持する。`packages/memora_android_widget_toast/`のAndroid namespace・Kotlinパッケージ・配置・`pubspec.yaml`のプラグイン登録も合わせる。
3. `home_widget_android_widget_cache_storage.dart`・`home_widget_calendar_cache_storage.dart`のReceiver完全修飾名、Androidウィジェットのaction名とManifestのintent-filterを更新する。関連する固定文字列・ソースファイルパスの参照も新しい名前にそろえる。
4. 新しいFirebase Androidアプリに対応する`android/app/google-services.json`を取得し、FlutterFire設定を再生成して`lib/firebase_options.dart`・ローカルの`firebase.json`を新しいFirebase App IDへ合わせる。利用中の認証設定を維持し、Git管理対象外の設定ファイルを強制追加しない。
5. iOS・macOSの`Runner.xcodeproj/project.pbxproj`にあるRunner/RunnerTestsのBundle ID、macOSの`Runner/Configs/AppInfo.xcconfig`、Linuxの`CMakeLists.txt`の`APPLICATION_ID`、macOS・Windowsの`com.example`名義の著作権・CompanyNameを正式な識別子・公開者表記へ変更する。未対応プラットフォームの新規対応は含めない。
6. READMEのFirebase設定・ADB操作のapplication IDと、識別子を記載している導入・配布手順を更新する。Google Play等で配布済みの場合は、下表の別アプリ扱いに合わせて配布先も用意する。

変更に合わせて扱う外部設定は以下とする。現時点ではConsole上の登録状況・公開状況は未確認。

| 対象 | 変更時に行うこと |
| --- | --- |
| Firebase Console | 既存Androidアプリのパッケージ名は変更できないため、同じプロジェクトへ新しいオンライン版のAndroidアプリを追加し、利用する署名証明書を登録する。Firebase App IDが変わるため設定ファイルも更新する。[公式手順](https://firebase.google.com/docs/android/setup) |
| Google CloudのAndroid OAuthクライアント | Googleログイン等で利用している場合、新しいパッケージ名とdebug・releaseそれぞれの署名SHA-1の組でクライアントを用意する。Play App Signing利用時は配信APKのアプリ署名証明書を使う。端末カレンダー連携のためのOAuth設定は不要。[署名証明書の確認](https://developers.google.com/android/guides/client-auth) |
| Maps・PlacesなどのAPIキー | Androidアプリ制限に新しいパッケージ名と署名SHA-1を登録する。旧版を併存させる間は旧設定の削除を急がず、既存のAPI制限を維持する。[制限の設定](https://developers.google.com/maps/api-security-best-practices) |
| Google Play（配布済みの場合） | application IDが変わると別アプリとなり、既存掲載への更新として配布できない。新規掲載・配布先を用意するか、既存IDを維持するかを実装前に判断する。[application IDの扱い](https://developer.android.com/build/configure-app-module) |
| Apple側の登録（利用済みの場合） | iOS・macOSのBundle ID変更に合わせ、Apple DeveloperのApp ID・署名プロファイル・利用中の外部サービスのアプリ登録を更新する。未登録のサービスをこの作業だけのために新規導入しない。 |

### アプリ識別子と既存インストールの扱い

- **推奨候補（未決定）**: オンライン版を`io.github.taka016.memora`、オフライン版を`io.github.taka016.memora.offline`とする案。GitHub名`taka-016`からハイフンを除いて利用者名に由来する識別子とし、アプリの表示名とは分ける。利用先での識別子の重複は採用前に確認する。保有する独自ドメインがある場合は、その逆順を接頭辞にする案も比較する。
- **既存インストール**: application ID変更後はAndroid上で別アプリとなり、旧版のSQLite・端末設定・ログイン状態・端末カレンダーの表示設定・ホーム画面ウィジェットは自動では引き継がれない。旧版の併存・削除時期と、必要なデータ引継ぎの範囲を決める。オフラインデータを残す場合は現行形式のバックアップの手動復元を候補とし、旧形式互換や自動移行を追加する前提にしない。
