### 所属に基づくFirestoreのアクセス制御

個人用グループの非公開性は、画面上の絞り込みに加えてFirestoreルールで保証する方針を採用する（[ストーリー26](user_stories.md#26-ユーザーとして自分だけの予定や年表を管理したい他の人と共有する記録と個人の記録を分けたいから)）。ルールの実装・適用は未着手。

1. 所属を判定できるよう、認証アカウントとメンバー・所属情報の参照、および関連データの取得条件を整理・修正する。
   - グループ、予定・個別回・ラベル、年表に表示する旅行・グループイベント・メンバー別イベントと、その関連データを対象にアクセス経路を確認する。
   - 本人の所属情報の取得、グループ作成、招待・参加、所有者・管理者による編集を維持する。本人が所属していないグループへの権限を自分で付与できる経路を作らない。
   - 通常画面・オンライン自動更新・Androidウィジェットの取得条件を認可の範囲と整合させる。ルール評価に伴う参照・通信への影響と、既存の取得・保存処理に必要な変更を具体化する。
2. `firestore.rules`を更新し、所属外の利用者による対象グループのデータの読み取り・書き込みを拒否する。
   - 一覧取得とID指定の直接取得の両方を対象とし、関連データを直接指定しても制限を回避できないようにする。
   - メール確認済みユーザーに広く許可する既存ルールを見直し、別の許可条件から所属制限を回避できないようにする。
   - カレンダーの予定・個別回と、年表の記録（旅行・グループイベント・メンバー別イベント）は、所属メンバー全員が追加・編集・削除できる。所有者・管理者であることや、その記録の作成者であることは条件にしない。グループ自体を管理する権限とは分けてルールに実装する。
   - 任意ラベルの追加・編集・並べ替え・削除も所有者・管理者だけに許可する。一般の所属メンバーによる予定保存に伴うラベル使用状況の更新とは区別する。
   - グループの編集・削除は所有者・管理者だけに許可する。現状はアプリ側で管理対象一覧を絞り込むだけで、Firestoreルールにはこの認可がないため、新たにルールで強制する。
   - 所属メンバーの追加・解除や管理者設定の変更にも対応する権限判定を適用する。通常のグループ編集による変更と招待・参加に必要な操作を区別し、一般メンバーが自分を管理者に変更したり所有者を書き換えたりして制限を回避できないようにする。
   - 権限判定には更新前の所有者・所属・管理者情報を使い、同じ保存要求に含めた権限変更によってその要求自体を許可しない。グループ作成時の所有者・本人所属の登録と、招待・参加はそれぞれ正当な操作として扱う。
   - 予定のグループ変更は変更元・変更先の両方への所属を必要とする。
   - 所属解除後のサーバーへの取得・更新要求を拒否する。すでに取得済みのデータを他端末から回収・消去する保証は含めない。
   - 既存の集約単位の保存と競合検出を維持する。オフライン版のローカルデータにはFirestoreルールを適用しない。

## カレンダー

[ユーザーストーリー23・24・26](user_stories.md#23-ユーザーとして家族や友人の予定を記録し日付ごとにまとめて把握したい互いの予定を見落とさず調整したいから)に対応する。個人用グループは自分だけが所属する通常のグループとして手動作成し、年表は既存のグループ単位の選択を維持する。実装は未着手。

1. 表示対象グループの端末内設定を追加する。
   - 自分が所属する有効なグループIDを複数保持し、初期値は空とする。既存のグループ選択やウィジェット設定から暗黙に引き継がない。
   - オンラインではアカウントごと、オフラインでは端末内の利用者ごとに設定を分離し、別端末へ同期しない。
   - 再表示・再起動時は最後に確定した選択を復元する。脱退・削除したグループは表示・選択対象から外し、所属一覧の取得失敗では保存済み選択を消さない。
2. カレンダーの入口を、グループ選択画面からカレンダーの直接表示へ変更する。
   - 右上に「表示するグループ」を設け、所属グループのチェックボックスで複数選択・全解除できるようにする。確定で保存・反映し、キャンセルでは変更しない。
   - 設定がなければグループの予定を表示せず、表示設定への案内を出す。所属が1つでも自動選択しない。
   - 月・週・日別の予定を選択グループ分まとめ、予定の詳細には保存先グループ名を表示する。同名の予定もグループと予定の識別子で区別する。
   - グループごとのオンライン自動更新・オフラインの保存後再取得と手動更新、および既存の編集競合検出を維持する。一部グループの取得失敗時も取得済みの他グループの予定を確認でき、失敗した対象と再試行の手段が分かるようにする。
   - 端末カレンダーの表示選択はグループの表示選択から独立させる。グループ未選択でも選択済みの端末カレンダーは表示する。祝日・六曜などの暦情報もグループ選択に依存させず既存の表示設定に従う。
   - 表示グループの設定はカレンダー・日別予定ウィジェットでも共用する。ウィジェット・通知からの遷移の詳細は末尾の検討保留で扱う。
3. 予定の新規登録・編集に保存先グループのプルダウンを追加する。
   - 候補は表示設定にかかわらず自分が所属する有効なグループのみ。未選択では保存できず、所属がない場合は作成・参加が必要だと案内する。
   - 新規登録は設定画面の既定グループを使い、編集は予定の保存済みグループを使う。
   - ラベル候補を選択グループの固定ラベル・任意ラベルに限定する。既存の所属解除・削除済みメンバーのラベル表示は、グループを変えない編集で維持する。
   - グループを変更するたびにラベルを変更先の「グループの予定」へ戻す。元のグループに戻しても以前のラベルは復元しない。未選択時はラベルも選択できない。
   - グループ変更だけではタイトル・日時・詳細・通知を変更しない。表示対象外へ保存する場合は、現在のカレンダーに表示されないことを案内し、表示設定は自動変更しない。
4. 既存予定の保存先グループを変更できるよう、オンライン・オフラインの保存処理を変更する。
   - 現在のRepositoryはグループ変更を拒否するため、入力欄の変更に加えて移動を扱えるようにする。変更元・変更先とも自分の所属グループに限る。
   - 保存前に変更先との共有になることを明示する。予定IDを維持して移動し、変更元への複製や取り残しを発生させない。キャンセル・保存失敗では変更前の予定を維持する。
   - 繰り返し予定のグループ変更は系列全体に限り、個別回だけの移動は提供しない。系列全体の変更になることを保存前に明示する。
   - 系列と全個別回を一緒に移し、系列・個別回のラベルを変更先の「グループの予定」へリセットする。日時・タイトル・詳細・通知の個別変更、繰り返し条件、個別の取消しは保持する。
   - 既存の予定と個別回の集約単位での保存・競合検出、および任意ラベルの使用状況管理を維持する。グループ変更に必要な参照・使用状況の更新を移動と合わせて扱う。
   - 変更元・変更先の表示を更新し、現在の表示設定に従って結果を反映する。既定グループと表示グループは変更しない。
5. 通知対象の取得・予約をカレンダーの表示グループから独立させる。
   - 表示に選んでいないグループも含め、自分が所属する有効な全グループの予定を対象に、予定・個別回の通知設定に従って通知する。既存の通知利用設定とOSの通知権限の条件を維持する。
   - 表示グループの選択・解除だけでは通知対象を増減させない。脱退・グループ削除・予定移動後は所属先と予定の通知設定に合わせて予約を更新する。
6. 表示グループと予定追加の既定グループを、オフラインバックアップの保存・復元対象から除外する。
   - 端末内の利用者ごとの設定として保持し、復元データからこれらの設定を読み込んだり上書きしたりしない。

1. 下表に従い、新しいオンライン版の識別子に対応するFirebase・Google Cloudのアプリ登録と認証設定を用意する。同じプロジェクトのAuthentication・Firestoreデータを引き続き使い、プロジェクトや既存データを作り直さない。
2. `android/app/build.gradle.kts`の`applicationId`・`namespace`と、`android/app/src/main/kotlin/com/example/memora/`配下のパッケージ宣言・配置を新しい名前へ変更する。オフライン版の`.offline`サフィックスを維持する。`packages/memora_android_widget_toast/`のAndroid namespace・Kotlinパッケージ・配置・`pubspec.yaml`のプラグイン登録も合わせる。
3. `home_widget_android_widget_cache_storage.dart`・`home_widget_calendar_cache_storage.dart`のReceiver完全修飾名、Androidウィジェットのaction名とManifestのintent-filterを更新する。関連する固定文字列・ソースファイルパスの参照も新しい名前にそろえる。
4. 新しいFirebase Androidアプリに対応する`android/app/google-services.json`を取得し、FlutterFire設定を再生成して`lib/firebase_options.dart`・ローカルの`firebase.json`を新しいFirebase App IDへ合わせる。利用中の認証設定を維持し、Git管理対象外の設定ファイルを強制追加しない。
5. iOS・macOSの`Runner.xcodeproj/project.pbxproj`にあるRunner/RunnerTestsのBundle ID、macOSの`Runner/Configs/AppInfo.xcconfig`、Linuxの`CMakeLists.txt`の`APPLICATION_ID`、macOS・Windowsの`com.example`名義の著作権・CompanyNameを正式な識別子・公開者表記へ変更する。未対応プラットフォームの新規対応は含めない。
