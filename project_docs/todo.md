## Firestoreの無料枠を活かすために読み取りを計測し、削減候補を絞る

オンライン版の不要な読み取りを減らし、Firestoreの無料枠内で利用できる規模を広げる。Firestore Standardの無料枠は1日5万読み取り。日次の枠に対する消費は本番の利用量で確認し、どの操作で読み取りが増えるかはエミュレータで再現する。エミュレータの観測値は操作間・変更前後の比較に使う。[Firestoreの無料枠と課金ルール](https://firebase.google.com/docs/firestore/pricing)・[利用量ダッシュボードの計上範囲](https://firebase.google.com/docs/firestore/monitor-usage)

以下の小節を記載順に1本ずつのPRで進める。削減実装は実測後に候補ごとに判断する。

- 計測処理はテストコード・エミュレータ設定・外部スクリプトに置く。通常のアプリコードに計測用のログ・フックやFirestore SDKのラッパーを追加しない。通常のビルド設定とFirestoreルールは原則維持する。
- Firestore SDKのキャッシュ設定と取得方式は通常どおりとする。計測目的で永続キャッシュを無効化したり、取得元をサーバーに固定したりしない。
- テスト側またはエミュレータ側から観測できた値を比較に使う。SDK内部の動作など観測できない項目は欠測とし、対象と比較への影響を記録する。欠測を埋めるためにアプリ側へ計測処理を追加しない。

### PR 1 — 日次の利用量と読み取り経路を整理する

- 対象データベースの日次読み取り、ピーク時の利用量、無料枠の残りの見方を整理する。集計は無料枠のリセットに合わせて太平洋時間の日単位とし、利用量ダッシュボードと課金レポートの差を明記する。取得できる既存の集計を基準値とし、権限や運用実績がなく取得できない値は未確認とする。
- 起動・アカウント／共有管理、カレンダー、年表、旅行／地図、DVC、通知、両Androidウィジェットの読み取り経路を一覧化する。画面の取得・購読、トランザクション、保存後の再取得、バックグラウンド処理を含める。操作頻度、データ増加、複数経路での重複が日次消費に影響しそうな箇所を挙げ、後続PRで計測する代表操作と条件を選ぶ。

### PR 2 — 代表操作1件をエミュレータで計測する

- 既存のエミュレータ環境を利用し、専用のデモプロジェクトでFirestore／Auth EmulatorとAndroidエミュレータを動かす。テスト側から接続先を指定し、本番への通信を遮断した状態で、実Firestore SDKを使うオンライン版の代表操作1件を再現する。
- テスト用JSONで投入データ・操作条件を固定し、テスト側またはエミュレータ側で読み取りを観測する。操作、取得先、取得・購読の回数、取得文書数、購読の初回・更新分のうち観測できる値を記録する。データ投入や結果照合の読み取りは除外し、計測できない値は欠測として出力する。
- `just test-firestore-reads`に起動・投入・操作・結果保存・終了をまとめる。成功時と中断・失敗時に、この実行で起動した資源を回収する。同じ条件で再実行して結果を比較できるようにし、READMEに起動前の準備を記載する。

### PR 3 — 起動とカレンダーの繰り返し操作を計測する

- キャッシュなしの初回起動、キャッシュが残る再起動、ログイン・アカウント／グループ切替で、利用可否・所属・メンバーなどの共通データを何回取得するか記録する。
- カレンダーの初回表示、新しい月への移動、表示済み月への往復、予定変更の受信を追加し、取得・購読の重複と差分受信を記録する。表示済み月の再取得・再購読は[ADR-009](adr/adr-009-calendar-month-subscription-cache.md)の既存の購読回数テストと照合する。

### PR 4 — 通知・ウィジェットの取得と再接続時の重複を計測する

- 通知の初回・定期・予定変更時の同期と、カレンダー／旅程ウィジェットの配置・更新を対象に、未配置・配置済み、アプリの起動中・終了後の条件で実際のAndroid側の起動経路を使って計測する。
- 画面とバックグラウンド処理を同時に動かす条件、通信断から復帰する条件を追加し、同じ予定・所属データの再取得や再購読を記録する。操作区間にひも付けられない読み取りは、区間全体の値または欠測として記録する。

### PR 5 — 履歴の蓄積による読み取りの増加を計測する

- 年表・旅行／地図・DVCについて、表示対象の件数を固定し、過去のメモ、旅行と子データ、ポイント利用履歴だけを増やしたデータセットで、初回表示・範囲変更・再表示の読み取りを比較する。

### PR 6 — 保存時と保存後の読み取りを計測する

- グループ／メンバー・招待、予定、旅行、DVCの代表的な更新操作を追加する。保存処理中の読み取りと保存後に連動する再取得を記録し、変更対象外の読み取りがどれだけ増えるか比較する。

### PR 7 — 無料枠への影響で候補を優先付けし、主要経路に回帰判定を追加する

- 操作別の計測値と想定する日次の操作・同期回数を使い、[検討保留の削減候補](#firestoreの読み取り削減の追加候補優先度5以降)も含め、日次に削減できる読み取り数と無料枠への影響を比較する。頻度が不明な操作は前提を示して利用規模別に試算し、取得可能な本番の日次集計と照合する。空のクエリの最低読み取り、インデックス、ルール評価用の読み取り、購読の再接続など、本番で加わり得る要因と未計測項目を明記する。インデックス調査が候補の順序を左右する場合は、Query Explainの対象と実行コストを整理する。
- 日次への影響が大きく再現性のある操作について、根拠付きの取得・購読・文書数の上限をJSONに定義し、超過・未実行・欠測を`just test-firestore-reads`で判定する。結果には対象操作・取得先・観測値・上限を残し、読み取りに影響する変更で同じ条件を再実行できるようにする。

### Firestoreの読み取り削減の追加候補（優先度5以降）

年表・旅行は現在少量だが、全履歴取得と広範囲の再取得を続けると蓄積に比例して読み取りが増える。以下は対応未決定の検討事項とする。

- **5. 年表の全年取得・広範囲の再取得**: グループと各メンバーのメモは全年分、旅行は初期状態で前後5年の計11年分を問い合わせる。復帰時の1分間隔の抑制を超えた更新や旅行保存時のProvider全体の無効化で再取得が増える。表示・追加表示する期間への限定と、変更したメンバー・グループ・年だけの更新を検討する。
- **6. グループID取得のための全メンバー取得**: 通知の所属ID取得でも画面用の全メンバー付きグループ取得を使う。認可文書のIDだけを取得する経路と、画面間の取得済みデータの共有を検討する。
- **7. 地図の全旅行・全地点取得**: グループ選択時と旅行変更後に全履歴を取得する。取得済みデータの部分更新、期間・地図範囲に応じた段階取得を、全履歴を一度に表示する仕様との兼ね合いで検討する。
- **8. 旅行保存時の全子データ取得・再作成**: タイトルだけの変更でも全場所・全タスク・全旅程を取得し、削除・再作成する。基本情報と子データの変更の分離を、既存の競合検出・一括保存を維持する範囲で検討する。
- **9. DVCの全履歴取得**: 計算画面は全契約・限定ポイント・利用履歴、年表は全利用履歴を取得する。過去の利用が現在の残高へ影響するため、必要期間と繰越情報の扱いを決めてから取得範囲の限定を検討する。
- **期間クエリのインデックス読み取り（影響未計測）**: カレンダーの開始・終了日時の2項目に範囲条件があり、返却文書以外の読み取りも増える可能性がある。Query Explainで走査量を確認してから、クエリ・インデックスの変更要否を判断する。
