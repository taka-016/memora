# ADR-011: 利用可否の確認を画面表示から分離し、データ更新を制御する

## ステータス

採用（実装は未完了）

## 決定日

2026-11-15

## コンテキスト

オンライン版では、サーバーのメンテナンス状態と最低対応ビルド番号を確認するまで、初回画面の表示を保留している。この通信待ちが通常起動・ウィジェット起動の両方に影響する。

利用可否の制御は、メンテナンス中や未対応バージョンからの更新によるデータ整合性への影響を防ぐことを目的とする。確認前の画面表示・閲覧・入力は許容でき、利用可否をアクセス認可の代わりにはしない。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| 利用可否の確認が終わるまで画面表示を待たせる | 不採用。確認前の閲覧・入力も止まり、起動時の通信待ちが発生する |
| 裏で確認し、確認前の表示・閲覧・入力を許容するが、データ更新は利用可能と確認できるまで待つ | 採用。入力開始を早めつつ、未確認・利用不可の状態での更新を防ぐ |
| 確認前でもデータ更新を許可する | 不採用。メンテナンス中や未対応バージョンで更新する可能性がある |

## 決定事項

- オンライン版の利用可否は起動時に非同期で確認し、画面表示の完了条件にしない。通常起動・ウィジェット起動に共通で適用する。
- 確認前の表示・閲覧・入力を許容する。メンテナンス中・更新必須の場合も、判明するまでこれらを利用できることを許容する。
- 追加・編集・削除などのデータ更新は、利用可能と確認できた場合に限り実行する。未確認・確認中の場合は確認を待ち、確認失敗時は更新せず再試行できるようにする。画面ごとに確認漏れが生じない共通の制御とする。
- 利用不可と判明した場合は操作を停止し、メンテナンスまたは更新必須の案内を表示する。通信失敗や利用不可の判定だけを理由に入力中の画面を破棄せず、入力内容を保持する。アプリ終了後の下書き保持は保証しない。
- 利用可能と確認済みの結果は共有し、更新のたびに必ずサーバーへ再確認する方式にはしない。サーバー側の状態変更を常時・即時に検知することや、利用可否の確認とデータ更新を原子的に行うことは保証しない。
- 認証・アクセス認可と既存の競合制御は維持する。オフライン版の利用可否にサーバー確認は追加しない。

## 決定理由

データ更新を行わない段階から通信完了を待たせるより、表示・閲覧・入力を先に許可する方が、起動時の待ち時間を減らせる。利用可能と確認できるまで更新を開始しないことで、確認前の操作を許容する範囲を明確にする。

利用可否はデータ整合性のためのアプリ側の制御であり、読み取りを含めた即時のアクセス遮断は要件としない。確認結果の共有により、操作のたびの追加通信を避ける。

## 結果

- 利用可否を確認する通信の完了待ちを、画面表示・入力開始までの時間から外せる。
- 確認より先にデータ更新を要求した場合は、その時点で待ち時間が発生する。
- 利用不可の判明前には、メンテナンス中や更新必須でも閲覧・入力できる場合がある。
- 更新処理を共通の利用可否制御へ接続する必要がある。確認失敗時は入力を保持して再試行できる状態にし、利用不可の場合は案内を優先する。
