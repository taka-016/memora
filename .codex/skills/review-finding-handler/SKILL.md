# レビュー指摘への対応

レビュー指摘を事実確認と対応判断に分けて扱い、今回の作業範囲で必要な修正まで行う。明示的にレビュー結果だけを求められた場合は、その依頼範囲を優先する。

## 妥当性の確認

各指摘について、対象差分を比較元から確認し、次を順に調べる。

1. 変更の目的と、指摘が述べる技術的事実は何か。
2. 前提となる操作、状態遷移、ルート、ライフサイクルに、本番構成と現行仕様で到達できるか。テスト専用構成だけを根拠にしない。
3. 到達できる場合、表示・操作、Firestore・SQLite等の正本、ハング・クラッシュ・復旧可能性にどの影響があるか。
4. 既存の別変更で解消済みか。提案された修正がPR目的や設計と整合し、影響に対して過剰でないか。

技術的に正しい指摘でも、現行仕様で前提が成立しない場合は将来要件向けの防御を追加しない。今回の差分に到達不能な防御コードや本番構成を再現しないテストがすでに含まれる場合は、削除が最小の是正か確認する。`対応する`、`対応不要`、`要確認`に分類し、理由と実際の発生条件を記録する。仕様や設計の判断が分かれ、ローカルの根拠では決められない場合はユーザーへ確認する。

## 同じ原因の調査

指摘の根本原因を短く言語化し、同じ関数・状態・Provider・UseCase・共通部品を使う経路、同じ責務や制御構造の箇所、このPRで同様に変更した箇所を調べる。通常操作に加え、連続実行、逆順、失敗、再試行、破棄、遅延完了を確認する。検索語は指摘文だけでなく、原因のAPI・型・呼び出し元・変更前後の実装から選ぶ。関連ケースにも同じ分類を適用する。

## 修正

- `対応する` と判断した指摘と関連ケースを、問題を解消する最小範囲で修正する。仕様上重要な振る舞いと失敗経路をテストし、関連テストと必要な全体検証を実行する。
- 修正と検証を終えたらコミットし、判定結果、関連ケースの調査範囲、修正内容、検証結果を呼び出し元へ返す。再レビューの要否判断と実行は呼び出し元の責務とする。
- 作業目的を超える変更、大きな設計判断、運用負荷が高い対応は、影響と案を整理してユーザーに確認する。対応不要の指摘は、到達不能または軽微と判断した具体的な根拠を説明する。

GitHub上の未解決スレッド取得、返信、解決は`github-pr-review-handler`の責務とする。
