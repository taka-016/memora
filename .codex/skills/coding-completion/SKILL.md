# Coding Completion

コード変更を完了する前に、このリポジトリで求められる締め手順を揃える。

## 基本方針

- ユーザーが`todo`更新の省略を明示した場合は、その指示を優先する。
- 併用する専門スキルが対象作業の`todo`更新を不要と明示している場合は、その専門スキルを優先する。
- このスキルは、`coding`で必要なコード変更とコミットが完了していることを前提に使う。
- 検証や最終確認で修正が必要になった場合は完了作業を中断し、`coding`に戻って修正とコミットを完了してからやり直す。
- ユーザーがpush、PR作成の省略を明示していない限り、完了条件にはそれらを含める。

## PR単位のバージョン管理

- PRの比較元ブランチとの差分全体から、利用者に対する変更内容を判断する。コミットのtypeだけで判定せず、バージョン更新自体は判定対象から除く。
- 不具合修正のみならパッチ、機能追加を含むならマイナーを上げる。ドキュメント、テスト、外部の振る舞いを変えない内部整理のみなら変更しない。
- `0.x`期間の互換性を壊す変更はマイナーの対象とする。メジャー変更や正式版への移行が必要と考えた場合は、影響と候補を提示してユーザーの判断を待つ。AIの判断だけで上げてよいのはマイナーまでで、`0.x`から`1.0.0`への移行を含め、メジャーは必ずユーザーが判断する。
- `pubspec.yaml`のバージョン名を更新する。パッチは末尾を1増やし、マイナーは中央を1増やしてパッチを0にする。`+`以降のビルド番号は変更せず、Firestoreの採番値・最低対応ビルド番号・メンテナンス設定も変更しない。
- 比較元ブランチのバージョンからPRにつき1回だけ更新する。同じPRの追加実装やレビュー修正では、変更全体を再判定して必要なら更新区分を変更するが、作業ブランチの更新済みバージョンに重ねて加算しない。
- ユーザーがバージョンを明示した場合は、その指定を自動判定より優先する。
- PR本文に変更前後のバージョン、更新区分、判断理由を記載する。変更しない場合も理由を記載する。

## 手順

1. `git status`と直近のコミットを確認し、`coding`で必要なコミットが完了していることを確認する。未コミットの差分がある場合は`coding`に戻る。
2. 「PR単位のバージョン管理」に従って更新要否を判断し、必要な`pubspec.yaml`の変更をコミットする。
3. ドキュメントのみの差分の場合は`just check`を実行しない。コード、設定、生成物、テストに差分がある場合は`just check`を実行し、エラーが残っていないことに加えて、テスト出力に予期しないExceptionログやエラーログが出ていないことを確認してから完了作業に進む。エラーまたは予期しないExceptionログが出た場合は`coding`に戻る。`just check`の実行によって発生した差分はこのタイミングでコミットする。
4. ユーザーまたは併用する専門スキルによる`todo`更新の除外がなければ、作業に対応する`project_docs/todo.md`の項目を削除する。
5. ユーザーまたは併用する専門スキルによる`todo`更新の除外がなければ、今回作業指示された`project_docs/todo.md`の項目が残っていないことを確認する。
6. プルリクエストの作成、既存プルリクエストへのpush・本文等の更新、レビューコメントへの返信を行う前に`independent-review`を適用し、その判定と手順に従う。
7. 独立レビューから指摘が報告された場合は完了作業を中断し、`review-finding-handler`を適用して妥当性を判断する。`対応する`と判断した指摘は、`coding`を適用して修正・検証・コミットする。修正が発生した場合は`independent-review`を再度適用し、新たな指摘が報告された場合は同じ手順を繰り返す。
8. 独立レビューを実施できない場合や`対応する`と判断した指摘が未解決の場合は、予定していたプルリクエストの作成・更新、push、レビューコメントへの返信を行わず状況を報告する。
9. ユーザーがpushやプルリクエスト作成の省略を指示していない場合、手順6から8を完了してからpushし、プルリクエストが未作成なら作成する。
10. `todo`更新を行った場合、プルリクエストの説明には完了(削除)した作業対応項目を記載する。

## 実行上の注意

- 検証が失敗している状態で完了扱いにしない。
- `just check`が成功していても、テスト中に予期しないExceptionログやエラーログが出ている状態で完了扱いにしない。
- `coding-completion`内で新たな修正差分を抱えたまま完了させない。差分調整が必要なら`coding`へ戻す。
