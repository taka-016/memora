# Test Coding

このリポジトリでテストコードを書きたいときは、このスキルを使って既存構成とテスト実行時の安定性を優先する。

## 基本方針

- ユーザーストーリー、業務上の不変条件、利用者から観測できる振る舞い、失敗時の復旧可能性を保護するテストを優先する
- テスト追加前に、同じ振る舞いが別の層ですでに十分検証されていないか確認し、その責務を持つ最も内側の層でテストする
- Notifierの状態遷移、再取得、排他制御はNotifierテストで検証し、Widgetテストでは主要操作から表示、Dialog・Snackbar、画面遷移へ接続できることに絞る
- ユニットテストのディレクトリ構成は`lib/`と同じにする
- テスト命名は`xxx_test.dart`とする
- 外部依存関係にはMockitoを使用したモックを基本とする
- 外部依存や抽象インターフェースを差し替えるテストで、単純な戻り値、例外、呼び出し検証で足りる場合はMockitoの`@GenerateMocks`または`@GenerateNiceMocks`で生成したモックを使用する
- 新しい振る舞いの追加、振る舞いの変更、バグ修正では、実装コードより先に失敗するテストを書くか既存テストへ失敗ケースを追加する
- 外部から観測できる振る舞いを変えないリファクタリングに備えて、現在の振る舞いを記録する特性テストを追加する場合は、失敗を必須とせず、変更前の実装で成功することを確認する

## テスト対象の選び方

- モックのスタブ値、テスト内で組み立てた定数、Flutterや`Equatable`など外部ライブラリ自体の動作だけを確認するテストは作成しない
- DTOとEntityでは、単純なコンストラクタ代入や全フィールドの機械的な`copyWith`確認を網羅しない。独自の値変換、nullable項目の明示的な解除、等価性が業務処理へ影響する項目、Domainの不変条件とバリデーションを検証する
- 異なるインスタンスの`hashCode`が必ず異なることを前提にしない。同値なら同じ`hashCode`になる契約だけが必要である
- 例外を捕捉、変換、補償処理しない単純な委譲処理では、下位層の例外がそのまま伝播することだけのテストを作成しない。引数変換、呼び出し順序、複数処理、トランザクションなど固有の責務がある場合に検証する
- 同じ結果を複数の画面階層や操作経路で重複検証せず、代表的な正常系と仕様上重要な失敗・再試行・競合ケースを残す
- 類似する入力境界や同型の操作は、可読性を損なわない範囲でパラメータ化や共通ヘルパーにまとめる

## Widgetテストの粒度

- 座標、固定幅、固定高、Widget間のpx単位の間隔、改行位置、背景色、内部Widgetツリーなど、利用者の操作結果に影響しない実装詳細を固定しない
- 色やアイコンなどを検証する場合は、警告、操作可否、アクセシビリティなど仕様上の意味があるものに限定する
- Safe Area、長文、多数項目、小さい画面については、特定の余白値ではなく、例外やオーバーフローが発生せず、内容をスクロールでき、必要な操作を実行できることを確認する
- 並び順を検証するときは、可能なら座標比較ではなく、生成したデータやWidgetの意味的な順序を確認する
- 表示要素の存在確認だけで終わらせず、重要な操作または状態との接続を同じテストで確認できる場合は統合する

## テストファイル

- ユニットテスト: `test/unit/`
- インテグレーションテスト: `test/integration/`

## テストベストプラクティス

- 生成モックの扱い: `**/*.mocks.dart`は生成物をコミットしないために`.gitignore`で除外しているだけであり、生成モックの作成や利用を禁止する意図ではない。生成モックが必要な場合は、テストファイルに生成アノテーションと`*.mocks.dart`のimportを追加し、`dart run build_runner build --delete-conflicting-outputs`で生成してからテストを実行する。生成された`*.mocks.dart`は通常コミットしない

- Fakeの使い分け: 状態遷移やProviderの生存期間など、テスト固有の振る舞いを小さく表現するFakeは必要に応じて使用してよい。生成モックへ無理に置き換える必要はない

- テストでの例外発生: テストで例外を発生させる場合は、必ず`test/helpers/test_exception.dart`の`TestException`を使用すること。`TestException`はログ出力を抑制するため、テスト実行時のノイズを減らすことができる

  ```dart
  // ❌ 避けるべき方法
  when(mockUseCase.execute()).thenThrow(Exception('エラーメッセージ'));

  // ✅ 推奨する方法
  import '../../../helpers/test_exception.dart';

  when(mockUseCase.execute()).thenThrow(TestException('エラーメッセージ'));
  ```

- 非同期テストの制御: `Future.delayed`を使った待機は避ける。環境によって不安定になるため、`Completer`を使用してテストコードが非同期処理のタイミングを制御する

  ```dart
  // ❌ 避けるべき方法
  when(mockUseCase.execute()).thenAnswer((_) async {
    await Future.delayed(const Duration(milliseconds: 100));
    return result;
  });

  // ✅ 推奨する方法
  final completer = Completer<Result>();
  when(mockUseCase.execute()).thenAnswer((_) => completer.future);
  // テストコードで完了タイミングを制御
  completer.complete(result);
  ```

- Widgetテストの待機: `pumpAndSettle`を無条件に使用せず、必要なフレーム、アニメーション、非同期完了だけを`pump`や`Completer`で制御する。継続的なアニメーションがある画面で`pumpAndSettle`へ依存しない

- 時刻の固定: テスト内で`DateTime.now()`へ直接依存せず、`AppClock`を固定時刻へ差し替える。月末、年末、日付変更のタイミングでも結果が変わらないようにする

- テストファイルの責務: 大きなWidgetテストは画面名だけで抱え込まず、通常操作、画面遷移、外部起動、状態復旧などの責務で分割する。同じ大規模なセットアップを必要とするだけの理由で無関係な仕様を同居させない
